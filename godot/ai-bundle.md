## TL;DR

Use the current stable Godot (4.7.2) with GDScript unless you have
a reason not to. Export to a device with the pre-built template
(APK); export for Google Play with a **Gradle build** (the only
route to the required AAB). Target API 36, ship from Godot 4.5 or
newer (16 KB page-size support), and commit everything except
`.godot/` and `*.translation` — including `export_presets.cfg`.

# AGENTS.md — rules for any AI working with Godot for Android

## The ground-truth hierarchy

1. The Godot documentation **for the exact engine version in use**
   (docs.godotengine.org has a page set per version — use the
   version switcher, never the first search result).
2. Google Play's own policy pages, for anything about publishing.
3. The project's own files (`project.godot`, `export_presets.cfg`,
   its pinned versions) for anything about the project.
4. This repo.
5. Community guides and videos — leads to verify, never authority.

## Non-negotiables

1. **Never invent** an API, an export option, a version number, or
   a Play requirement. If it is not on a fetched official page, it
   is marked Unverified or left out.
2. **Version-pin everything.** Godot's requirements change per
   release: JDK, SDK components, .NET floors, and Play targets in a
   tutorial for the wrong version are wrong answers. State the
   engine version in every plan and check the docs page for that
   version.
3. **Play releases need a Gradle build.** The pre-built template
   export produces APKs only; the AAB Google Play requires comes
   from the Gradle build (docs/03, docs/05).
4. **Ship Play builds from Godot 4.5+.** Earlier exports lack 16 KB
   page-size support and draw Play warnings (docs/05).
5. **GDScript is the default.** C# on Android is experimental and
   needs the .NET editor build; reach for it only with a stated
   reason (docs/04).
6. **Commit `export_presets.cfg`** (Godot 4.1+ stores no
   credentials in it); ignore only `.godot/` and `*.translation`
   (docs/02). Never commit a release keystore or its passwords.
7. **Plugins are v2.** The `.gdap` / `res://android/plugins` flow
   in old docs is deprecated (docs/06).
8. **Tests must prove they ran.** Headless runners can exit 0 with
   zero tests executed; a CI gate checks the count (docs/08).
9. **Free means free.** This family's games carry no ads, no paid
   unlocks, no data selling. Billing and ads are documented in
   docs/05–06 because the platform requires knowing them, not as
   features to add by default.

# 01 — The engine and its versions

Checked 2026-11-17 against godotengine.org and the official
Release Policy page.

## Where Godot stands

- **Current stable: Godot 4.7.2** (the 4.7 feature release shipped
  June 2026; the download page for 4.7.2 is dated August 2026).
  **4.8 is in development** (beta builds already listed).
- Support windows per the Release Policy: a stable branch is
  supported at least until the next branch's first patch release,
  and **only the latest patch release of a series receives
  support**. Patch releases are backwards compatible and strongly
  recommended; minor upgrades are case-by-case.
- Recent lines: 4.6 (Jan 2026, supported), 4.5 (Sep 2025, partial
  support — security and platform fixes only), 4.4 and older (end
  of life).

## Godot 3.x

Still maintained, but winding down and explicitly best-effort:
3.6 (Sep 2024) is a supported branch and still shipping patches
(3.6.3, Nov 2026, raised its default Android target SDK to 36);
3.7 exists only as development builds with no planned release
date, and the policy page says 3.6 may be the last stable 3.x
branch. The docs' own recommendation: **use Godot 4.x for new
projects** — the standing exception is a project needing a feature
4.x dropped (e.g. GLES2/WebGL 1.0).

## Rules this implies

- Start new Android work on the current 4.x stable, and keep the
  editor, export templates, and project on the **same** version —
  templates and editor must match exactly.
- Budget for a yearly minor-version move: Play's target-API floor
  rises every August (docs/05), and riding a supported Godot line
  is how a small project keeps up without heroics.
- Pin the version in the project's docs and CI image tag; "latest"
  is not a version.

# 02 — Project anatomy and version control

From the official Project organization and Version control systems
docs.

## What a project is made of

| Piece | What it is |
|---|---|
| `project.godot` | INI-style project file at the root: app name, main scene (`run/main_scene`), autoloads, input map, project settings. Committed. |
| Scenes | `.tscn` (text — readable, mergeable) or `.scn` (binary). Resources likewise: `.tres` text, `.res` binary. |
| Scripts | `.gd` (GDScript) / `.cs` (C#), kept beside the scenes they attach to. Paths are `res://`-rooted. |
| `addons/` | Top-level folder for editor plugins (each a subfolder with `plugin.cfg`, enabled under Project Settings → Plugins) and third-party resources generally — including Asset Store downloads and Android plugins. |
| `export_presets.cfg` | Project root; every export preset, including Android package name, version, architectures, permissions, keystore fields, and Gradle options. |
| `.godot/` | Editor cache (imported assets, UID cache, shader cache). Fully regenerable; never committed. |
| `android/` | Appears only after installing the Gradle build template; the generated Android project lives under `res://android/build`. |

Godot uses the filesystem as-is — no asset database, no metadata
files beyond `.import` sidecars next to imported assets.
Conventions from the style guide: group assets close to the scenes
that use them, snake_case file and folder names (C# scripts
excepted), and a `.gdignore` file stops the importer processing a
folder.

## Version control (Godot 4.1+)

The official ignore list is exactly two entries:

```
.godot/
*.translation
```

Everything else is source and is committed — `project.godot`,
scenes, scripts, `.import` sidecars, and `export_presets.cfg`.
That last one surprises people coming from old tutorials: Godot
3.x and 4.0 could store sensitive credentials in
`export_presets.cfg`; **4.1 and later do not**, which is why the
guidance flipped. (Keystore *passwords* still never go in the repo
— CI passes them by environment variable, docs/03.)

The Project Manager can generate the `.gitignore` / `.gitattributes`
for you (Project → Version Control → Generate Version Control
Metadata), enforcing LF endings; Windows Git users without the
generated metadata should set `core.autocrlf` to `input`. The docs
also provide a Git LFS starter for large binaries (models, images,
audio, fonts, and binary resources like `*.scn` / `*.res`).

# 03 — The Android export pipeline

From the official "Exporting for Android" and "Gradle builds for
Android" pages. **Component versions are pinned per Godot
version** — the numbers below are the current-docs set; the same
page for your exact editor version is the authority (a 4.4-era
page lists the 34-series SDK and NDK r23c, which are wrong for
current Godot).

## Prerequisites

1. **OpenJDK 17.** Higher JDK versions are supported; 17 is the
   recommended one for compatibility and stability. (Godot 4.0
   wanted JDK 11 and Godot 3 wanted JDK 8 — another version trap.)
2. **Android SDK** via Android Studio (Iguana 2023.2.1+) or
   `sdkmanager`. Current-docs component set:

   ```
   sdkmanager --sdk_root=<android_sdk_path> "platform-tools" "build-tools;35.0.1" "platforms;android-35" "cmdline-tools;latest" "cmake;3.10.2.4988404" "ndk;28.1.13356709"
   ```

   Platform-Tools must be 35.0.0 or later. On Linux, do not use a
   distro-packaged SDK — the docs warn it is often outdated.
3. **Export templates** matching the editor version, installed via
   Editor → Manage Export Templates.
4. **Point the editor at the toolchain** (Editor Settings →
   Export → Android): `Java SDK Path` and `Android Sdk Path`.
   These are per-user editor settings, not project files.

## The two export methods

**A. Pre-built template export (default).** Add an Android preset
(Project → Export) and export: Godot packages the project into the
pre-built template. Output is **APK only** — right for devices,
sideloading, and other stores, never for Google Play.

**B. Gradle build (required for Play).** Project → **Install
Android Build Template…** installs a Gradle project under
`res://android/build`; enable **Gradle Build** in the preset and
every export runs Gradle. Use it to:

- export an **AAB** for Google Play (the reason most projects
  switch),
- export an AAR to embed in another Android app,
- customize the Android template project,
- add Android/Java/Kotlin SDKs and libraries to the build.

The native `.so` stays precompiled — no C++ toolchain or engine
source build is needed. (Older docs call this "Custom builds";
same mechanism. Since Godot 4.6 the Android editor can also run
Gradle builds on-device via the separate Godot Android Build
Environment app.)

## Signing

- **Release keystore**, generated once and kept safe **outside**
  the repo:

  ```
  keytool -v -genkey -keystore mygame.keystore -alias mygame -keyalg RSA -validity 10000
  ```

  Fill the preset's Release / Release User / Release Password
  fields. Two documented gotchas: the keystore password and the
  key password currently **must be the same**, and passwords
  should use only letters and numbers — special characters may
  cause errors. Uncheck **Export With Debug** for release exports.
- **Debug builds** use the debug keystore settings; for headless
  and CI exports both keystores are supplied by environment
  variables: `GODOT_ANDROID_KEYSTORE_DEBUG_PATH/_USER/_PASSWORD`
  and `GODOT_ANDROID_KEYSTORE_RELEASE_PATH/_USER/_PASSWORD`, plus
  `GODOT_SCRIPT_ENCRYPTION_KEY` for script encryption.
- One-click deploy trap: a device holding the same package name
  signed with a different key must have it uninstalled first.

## Icons and size

- Main icon at least 192×192 px; adaptive-icon foreground and
  background at least 432×432 px; optional themed (monochrome)
  icon at least 432×432 px. Godot generates the lower densities
  and has a documented fallback chain.
- A default APK bundles both ARMv7 and ARMv8 libraries; uncheck
  an architecture in the preset to trim it. For AAB this is
  unnecessary — Google splits the bundle on their side.

# 04 — Languages: GDScript, C#, GDExtension

## GDScript — the default

Godot's own scripting language carries no Android caveats anywhere
in the docs, needs no special editor build, and is what the demo
projects, the Asset Store ecosystem, and this family's projects
use. Default to it.

## C# (.NET) — supported on Android, officially experimental

- Since **Godot 4.2**, C# projects can be exported to Android; the
  docs label Android support **experimental** in both the export
  page banner and the C# platform-support page. (The often-quoted
  "C# cannot be exported to Android" line is from the 4.0 docs and
  is simply outdated.)
- C# requires the **.NET build of the editor** from
  godotengine.org — the standard executable has no C# support, and
  store builds (Steam etc.) do not include it either.
- Documented limits (4.3 docs, the most detailed official
  statement): projects must target .NET 7.0 or higher, and only
  the `arm64` and `x64` Android architectures are supported. The
  current C# page keeps the experimental label without restating a
  version floor — **treat the exact .NET floor as version-pinned
  and check the C# platform-support page for your version** (a
  third-party guide claims .NET 9+; unverified against official
  docs, see SOURCES.md).
- The standing contrast: C# projects still **cannot** be exported
  to the web platform. Android is not the blocked platform; Web
  is.

## GDExtension — native code when you need it

GDExtension libraries ship per-platform, per-architecture entries
in their `.gdextension` config, Android included (`android.debug` /
`android.release` for arm64, x86_64, …). Godot 4.2+'s v2 Android
plugins can also bundle GDExtensions. Reach for GDExtension for
performance-critical or native-library work, not as a default —
every native library you ship joins the 16 KB page-size scope in
docs/05.

# 05 — Google Play: the hard requirements in force

Checked 2026-11-17 against Play Console Help and Android
Developers pages. These floors rise on a yearly cadence — re-check
before every release (SOURCES.md has the exact pages).

## AAB is mandatory for new apps

Since August 2021, new apps must publish as an **Android App
Bundle**, and enrolling in **Play App Signing** is mandatory to
use bundles. Apps created before August 2021 may still update as
APKs; TV app updates have required AAB since June 2023. For a
Godot project this means: Gradle build on, Export Format = AAB
(docs/03).

## Target API: 36 (Android 16)

- **New apps and app updates must target API 36 since
  August 31, 2026** (API 35 applied from August 2025; the
  extension window to Nov 1, 2026 is past).
- Existing apps must target API 35+ to stay available to new users
  on newer devices. Other form factors run lower floors (Wear OS
  35, TV 34, XR 34, Automotive 35).
- Godot side: the 4.7.2 build template is reported to compile
  against API 36 by default even though the docs' SDK list still
  shows the 35 series (templates ahead of docs — Unverified
  against engine source, see SOURCES.md); Godot 3.6.3 raised its
  default target to 36 as well. Verify the produced AAB's target
  SDK in Play Console rather than assuming.

## 16 KB memory page sizes

- Every app targeting API 35+ must support 16 KB page sizes on
  64-bit devices. Pure managed apps comply automatically; anything
  shipping native `.so` libraries is in scope — **every Godot
  export ships native libraries** (`libgodot_android.so`,
  `libc++_shared.so`), so every Godot game is in scope.
- The general fix is NDK r28+ (16 KB-aligned by default) with AGP
  8.5.1+. In Godot, support landed in **4.5** (built on NDK r28b);
  exports from **4.4.1 and earlier trigger Play warnings**.
  Practical rule: **never ship a Play build from Godot older than
  4.5.**
- Enforcement timeline: originally November 1, 2025, with an
  extension path to May 31, 2026; the current official hard line
  is that **from February 1, 2027, updates without 16 KB support
  cannot be released**.

## Play Billing Library 8+

For apps that bill through Google Play: PBL 7 stopped being
acceptable for new apps and updates on August 31, 2026 (extensions
ended November 1, 2026), so **PBL 8+ is required** (the library
itself is at 9.1.0, June 2026; PBL 8's own deadline is Aug 2027).
The Godot billing plugin (godot-sdk-integrations)'s current build bundles
billing-ktx 8.0.0 and satisfies this — older plugin builds may
not (docs/06).

> This family's games are free — no paid unlocks, no ads, no data
> selling (AGENTS.md rule 9). The billing facts above matter
> because Play applies its rules to anything that bills, and
> because a future donation or companion app still has to clear
> them.

# 06 — Android plugins

## The v2 plugin system (current since Godot 4.2)

- A v2 plugin is an Android library built against the Godot
  Android library; its init class extends `GodotPlugin`, its
  manifest entries use the `org.godotengine.plugin.v2` prefix,
  and it is packaged through an EditorExportPlugin into the
  project's `addons/` — **not** as a `.gdap` file. The `.gdap` +
  `res://android/plugins` flow in Godot 3 / 4.0–4.1 docs is
  **deprecated**; v1 plugins are legacy.
- Building or bundling a plugin requires a **Gradle build**
  (docs/03). Plugins are enabled per export preset.
- Official starting points: `m4gr3d/Godot-Android-Plugin-Template`
  and the GDExtension-Android-Plugin-Template on GitHub.
- Before writing a plugin for simple Java interop, check the
  built-ins: Godot 4.4 added the `JavaClassWrapper` singleton and
  a bundled `AndroidRuntime` plugin, which cover many cases that
  used to need a custom plugin.

## Play Billing — GodotGooglePlayBilling

- `GodotGooglePlayBilling` used to live in the godotengine org; its
  repo **moved** to
  **godot-sdk-integrations/godot-google-play-billing**. That org
  describes itself as hosting *community-maintained* SDK
  integrations that the Godot Foundation **does not maintain or
  endorse** (org description, checked 2026-11-27) — so treat it as
  the canonical community plugin, not as engine-supported code.
- Versioning: **1.x releases are for Godot 3; 2.0.0 and later are
  for Godot 4.** (Release 2.0.0 is the latest attested, Aug 2025 —
  check the releases page; see SOURCES.md.) The current build
  bundles **billing-ktx 8.0.0**, which satisfies Play's PBL 8+
  requirement (docs/05); it packages v2-style into
  `addons/GodotGooglePlayBilling/`.
- Purchases must be acknowledged or Google refunds them (the docs
  have said so since the Godot 3 era).
- Ignore the legacy Asset Library listing claiming a "Godot
  Google Play Billing 3.2.0" — its versioning matches nothing in
  the godot-sdk-integrations releases; provenance unverified. Get
  the plugin from the godot-sdk-integrations releases.

## AdMob — Poing Studios, in its new home

- The maintained AdMob plugin is **Poing Studios'**, now in the
  monorepo **poingstudios/godot-admob-plugin** (docs at
  poingstudios.github.io/godot-admob-plugin). The old per-platform

  - Needs a **Gradle build** (docs/03).

Checked 2026-11-27. There is **no** maintained, org-hosted

- **Write a thin v2 plugin** from `m4gr3d/Godot-Android-Plugin-Template`

  form. Whether it also needs user consent (EEA/UK) depends on what

# 07 — The Asset Store (and the Asset Library it replaced)

## Where addons come from now

- The **Godot Asset Store** (store.godotengine.org) is the current
  distribution channel: announced on the official blog as
  live/stable (beta began May 2026) and **integrated into the
  Godot 4.7 editor**. (The docs' Asset Store page still says
  "currently in beta" — the blog is the more recent statement;
  noted here so the discrepancy doesn't confuse.)
- The old **Asset Library** is **deprecated** and being set
  read-only. Assets were **not auto-migrated** — authors had to
  re-upload to the Store — so a missing or stale Store listing for
  a known addon usually means the author hasn't moved it yet; the
  project's GitHub releases are the fallback source.

## How an install lands in a project

Whichever storefront you use, the mechanics are the same:

1. The download lands in the project's **`addons/`** folder.
2. Editor plugins are enabled under **Project Settings →
   Plugins**.
3. Android plugins additionally need enabling in the Android
   export preset, and a Gradle build (docs/03, docs/06).
4. The addon becomes part of the project tree — commit it like
   any other source (docs/02), and record its version in the
   project docs, because storefronts do not pin versions for you.

## Choosing addons

- Prefer addons whose repo shows releases matching your engine
  version; an addon built for 4.2-era APIs may load in 4.7 and
  still misbehave.
- Check the license before bundling anything into a shipped game,
  and keep third-party code inside `addons/` — never copied into
  your own folders, where its origin gets lost.

# 08 — Testing and CI

## On a real device: one-click deploy

From the official One-click deploy docs: mark an Android export
preset **Runnable**, enable USB debugging on the device, and the
editor exports, installs, and runs a **debug build** in one step.
Wireless ADB works too. Remember the signing trap from docs/03:
same package name with a different key already installed means
uninstall first.

## Automated tests: Godot ships no framework

There is no built-in project test framework; the community
standards are both headless-capable:

| Framework | Version (Nov 2026) | Headless invocation |
|---|---|---|
| GUT (bitwes/Gut) | v9.7.1, targets Godot 4.7.x | `godot --headless --path . -s addons/gut/gut_cmdln.gd -gdir=res://tests -gexit` |
| GdUnit4 (godot-gdunit-labs/gdUnit4) | v6.2.3; ships its own GitHub Action | `GdUnitCmdTool.gd` — exits **103** unless `--ignoreHeadlessMode` is passed; test failures exit **100** |

Two traps, both confirmed on Godot 4.7.2:

1. **Headless mode does not deliver input events to Controls.**
   UI click tests need a virtual display (`xvfb-run`) instead of
   `--headless`.
2. **Both runners can exit 0 when zero tests ran.** A CI gate that
   only checks the exit code can pass an empty suite forever —
   assert the executed-test count in the report.

## CI builds: the godot-ci route

- **abarichello/godot-ci** is the community-standard route: Docker
  images (`barichello/godot-ci`) track Godot releases (a 4.7.1 tag
  was current in Nov 2026), in standard and `mono-` variants,
  bundling the Android SDK and a debug keystore, with example
  GitHub Actions and GitLab CI workflows. **iOS export is not
  supported.** No official Godot-org GitHub Action was found.
- Keystore credentials reach the export through the
  `GODOT_ANDROID_KEYSTORE_*` environment variables (docs/03) —
  CI secrets, never repo files.
- Treat the images' exact bundled SDK components as unverified
  (published lists look dated); if a build fails on a component,
  pin your own SDK install step rather than trusting the image's.

# 09 — Android permissions

From the EditorExportPlatformAndroid class reference (the full
export-option list lives there) and the export docs.

## Declaring permissions: the preset

The Android export preset carries a `permissions/*` option group:
one boolean per Android permission (for example
`permissions/camera`, `permissions/access_fine_location`) plus
`permissions/custom_permissions` for arbitrary permission strings
that have no checkbox. Declaring a permission puts it in the
manifest; it does not grant it at runtime.

## Requesting at runtime

Dangerous permissions must be requested from the user at runtime
from code, with the OS singleton:

- `OS.request_permissions()` — ask for the permissions the preset
  declared.
- `OS.get_granted_permissions()` — see what the user actually
  granted.

Design for denial: a refused permission is a normal state, not an
error — the feature that needed it degrades, the game carries on.

## Discipline

- Request only what a shipped feature uses. Play reviews
  permission declarations, and every unused permission is review
  surface and user distrust for nothing.
- The preset's other option groups are listed in
  [reference/android-preset-options.md](../reference/android-preset-options.md);
  when an option's meaning is in doubt, the class reference — not
  a tutorial — is the authority.

# 10 — Choosing a renderer for Android

Checked 2026-11-27 against the Godot **4.7** docs page "Overview of
renderers" (docs.godotengine.org → Tutorials → Rendering). Re-check
that page for the engine version you pin (AGENTS.md rule 2).

## The three renderers

| | Compatibility | Mobile | Forward+ |
|---|---|---|---|
| Driver | OpenGL | Vulkan, Direct3D 12 or Metal (RenderingDevice) | Vulkan, Direct3D 12 or Metal (RenderingDevice) |
| On mobile | Yes — low-end | Yes — high-end; **the mobile default** | Supported but poorly optimized; don't use |
| Runs without Vulkan | Yes | No | No |
| Old / low-end hardware | Fastest | Runs, slower than Compatibility | Slowest |
| Cost profile | Low base, high scaling | Medium base, medium scaling | High base, low scaling |
| Feature set | 2D + core 3D | Most features, limited by mobile hardware | All features |

Docs' starting rule: **Mobile** for newer mobile devices and 3D
with advanced features; **Compatibility** for older devices, for
the widest hardware range, for 2D, or when you want the best
performance and don't need advanced features. Every game is
different — measure on your minimum-spec device.

## Feature differences that matter on Android

Only in Mobile and Forward+ (not Compatibility): FXAA, SMAA, 2D
MSAA, screen-space roughness limiter, debanding, decals, **particle
trails**, particle SDF collision, depth-of-field blur, variable rate
shading, 2D HDR viewport, HDR output, CompositorEffects, compute
shaders (Mobile: with a performance penalty on older devices),
light projector textures, PCSS for omni/spot lights.

Only in Compatibility (not Mobile): **SSAO**.

In all three: **glow**, fog (depth and height), tonemapping,
adjustments, fullscreen-quad post-processing, 3D MSAA, SSAA,
screen and depth textures, ReflectionProbe (Compatibility 2 per
mesh, Mobile 8 per mesh).

Not on mobile renderers at all (Forward+ only): volumetric fog,
SSR, SSIL, SDFGI, VoxelGI, TAA, FSR2, sub-surface scattering.

Lights: Mobile allows 8 omni/spot lights per mesh and 256 per
view; Compatibility 8 per mesh (raisable), and lights with shadows
use extra passes with less accurate blending.

Color precision: Mobile renders RGB10A2 (RGBA16F with HDR 2D on);
Compatibility RGBA8. Bright, saturated neon looks can band or clip
differently between the two — compare on device.

## Fallback behavior

- Since Godot 4.4, Mobile/Forward+ fall back Vulkan ↔ Direct3D 12,
  and if RenderingDevice isn't supported at all the engine falls
  back to **Compatibility** so the game still runs — possibly
  looking different. Turn this off with *Rendering → Rendering
  Device → Fallback to OpenGL 3* if you'd rather fail than look
  wrong.
- Switching renderers can need scene, lighting and environment
  tweaks; Mobile ↔ Forward+ needs fewer than either ↔
  Compatibility. Decide early (pre-production) rather than late.

## Practical guidance for this family

- 3D mobile game with glow/particle-trail effects → start on
  **Mobile**, and keep a Compatibility test build so the fallback
  path is never a surprise.
- 2D game, or a 3D game that must run on old/cheap phones →
  **Compatibility**.
- Budget numbers (draw calls, particle counts) are project
  decisions, not engine facts — prove them on the min-spec device.

# Godot realistic physics resources

Scope: Godot **4.7.2** API and the **4.7** documentation branch, captured 2026-11-22. Recheck the target project's exact version before adapting. This is an offline research collection, not installed addons or a tested simulation.

## Start with the supported engine

- **SoftBody3D:** subdivide the mesh sufficiently, configure pinned points and collisions, and budget solver cost. The [official tutorial](../physics/vendor/godot-physics-manual/tutorials/physics/soft_body.rst) explicitly says soft body support is generally more robust with Jolt. New projects created in 4.6+ default to Jolt; existing projects may need the project setting changed. Physics interpolation currently does **not** affect soft bodies. More physics ticks can improve their smoothness at CPU cost.
- **Ragdolls:** use a Skeleton3D to generate physical bones, tune their shapes/joints, and use **PhysicalBoneSimulator3D.physical_bones_start_simulation()** in this version. See the [ragdoll tutorial](../physics/vendor/godot-physics-manual/tutorials/physics/ragdoll_system.rst) and [current API](../physics/vendor/godot-physics-api/doc/classes/PhysicalBoneSimulator3D.xml). Older tutorials may place control methods elsewhere.
- **Jolt:** read [backend differences and unsupported features](../physics/vendor/godot-physics-manual/tutorials/physics/using_jolt_physics.rst) before switching. Backend selection is not proof that a particular suspension, joint setup or project will be stable.
- **Interpolation:** [advanced interpolation](../physics/vendor/godot-physics-manual/tutorials/physics/interpolation/advanced_physics_interpolation.rst) explains camera/manual exceptions and local transform interpolation in both 2D and 3D. Update physics-driven transforms on physics ticks and reset interpolation after discontinuities where appropriate. Rendering smoothness does not increase physical accuracy.
- **Vehicles:** [VehicleBody3D](../physics/vendor/godot-physics-api/doc/classes/VehicleBody3D.xml) is a raycast vehicle with known issues and is **not designed for realistic 3D vehicle physics**. Prototype its behavior before choosing it; the official reference suggests custom CharacterBody3D/RigidBody3D integration for advanced needs. Jolt does not remove this limitation.

## Correctness rules to apply deliberately

1. **Callbacks:** [RigidBody3D._integrate_forces(state)](../physics/vendor/godot-physics-api/doc/classes/RigidBody3D.xml) is specifically intended for safe direct physics-state access. Do not prohibit it or defer every update. Scene-tree changes or collision changes while queries are flushing can require call_deferred/set_deferred; decide from the operation and exact error/API contract. Avoid repeatedly overriding a rigid body's transform/velocity from render callbacks.
2. **Layers and masks:** design and test both sides of collision filtering. Explicit values in scene files or code make intent reviewable; inspector defaults are not inherently invalid. Verify trigger monitoring, shapes, scale, and backend before blaming a missing collision on masks alone. See [CollisionObject3D](../physics/vendor/godot-physics-api/doc/classes/CollisionObject3D.xml).
3. **Time steps:** for an original manual continuous decay model, `speed *= exp(-rate * delta)` preserves the chosen exponential rate across time steps. Use consistent units and physics delta. Do not add it on top of built-in damping without accounting for both; engine damping has its own documented integration semantics. Apply impulses for impacts and forces for sustained acceleration.
4. **Performance:** increase tick rate or solver work only against a measured failure and CPU budget. Test piles, fast bodies, joint chains, soft meshes and worst-case contacts. Interpolation can smooth supported transforms without increasing tick rate; it cannot fix tunneling, invalid shapes or unstable constraints.
5. **Validation:** compare trajectories at multiple tick rates, verify units, rest stability, energy growth, collision filtering, high-speed contact and pause/resume. Benchmark on each target platform/backend. No tests here establish physical accuracy, determinism, performance or Android compatibility of community addons.

# Android export preset — option groups

The Android preset's options, grouped as the
EditorExportPlatformAndroid class reference enumerates them. The
class reference is the authority for exact names and defaults;
this page is the map.

| Group | Covers |
|---|---|
| `architectures/*` | Which ABIs to include (arm64, arm32, x86_64, x86) — trim for APK size; unnecessary for AAB |
| `package/*` | App name, unique name (the application ID), version code/name |
| `keystore/*` | Debug and release keystore path, user (alias), password — passwords come from env vars in CI, never the repo |
| `gradle_build/*` | Gradle build on/off, export format (APK/AAB/AAR), min/target SDK, and Gradle-specific settings |
| `custom_template/*` | Custom export template binaries, when not using the official templates |
| `apk_expansion/*` | APK expansion (OBB) settings for the legacy APK route |
| `permissions/*` | One boolean per Android permission + `custom_permissions` — see docs/09 |
| `screen/*`, `graphics/*` and display options | Orientation, immersion, rendering driver choices as listed in the class reference |

Preset files are committed (docs/02). When a tutorial names an
option that is not in the class reference for your version, the
tutorial is for a different version — that mismatch is the most
common export bug in this ecosystem.

      signed with the upload key; Google signs for distribution

      acknowledged (docs/06)
- [ ] Permissions declared = permissions used (docs/09)
- [ ] Tests ran in CI with the executed-count check green

# Examples

The canonical worked examples are upstream's:

- **godotengine/godot-demo-projects** — the official demo
  collection; the Android-relevant ones show the export and input
  patterns in real projects.
- **Google's Godot guides** on developer.android.com ("Install
  Godot and configure projects for Android", "Export Godot
  projects to Android") — the Play-side view of the pipeline in
  docs/03. Caution: their C# sections are Godot 3-era (Mono) and
  stale for Godot 4; the export flow itself is current.

And the family's own:

- **GodotDevTools** (github.com/SeanShaffer88/GodotDevTools) —
  141 dev-tool addons; their docks, CLIs, and CI gates are worked
  examples of editor tooling, headless checks, and shipping
  discipline for Godot 4 projects.

Read examples against the docs, not instead of them: an example
proves a pattern ran once, on one version; the docs carry the
version-pinned rules.
