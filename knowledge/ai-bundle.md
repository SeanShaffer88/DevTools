# DevTools

A self-contained knowledge base for building Windows desktop software
the way this family of projects is built: a layered rule system
(Elite Prompt → Engineering Contract → master prompts → project rule
sheet), tiered project classes with sanctioned stacks, a hard quality
gate, one packaging tool (SeanPak), one design system (TesselGUI),
and one release shape. Written for AI coding agents first and human
developers second.

## TL;DR

Building a Windows desktop program here means: classify the project
into its tier (docs/02), pick the tier's sanctioned stack, implement
every feature as an operation the GUI and CLI both call (docs/04),
follow the every-program rules (docs/06), theme it with TesselGUI
Carmine (docs/07), package it with SeanPak into exactly one installer
+ one portable zip + checksums (docs/08), and ship only when the
full gate passes and the release is verified by read-back (docs/09).
Software is free, offline, unsigned, and never on winget.

## Where this lives

This knowledge base is the `knowledge/` folder of the **DevTools**
repo, alongside that repo's Local Developer Toolkit (the
PowerShell/Python helper scripts at the repo root). The toolkit is
the tooling; this folder is the written system behind it.

# AGENTS.md — rules for any AI working in this system

You are building Windows desktop software under a layered rule
system. This file is the short form. The docs carry the detail; the
full source texts are named in [SOURCES.md](SOURCES.md) and win on
conflict with any summary, including this one.

## The layers, in force order

1. The owner's current instruction for the task at hand.
2. The Elite Software Master Prompt — governs all projects.
3. The Adaptive Engineering Contract (V4.0) — tiers, stacks,
   universals, override classes.
4. The AI Coding Guardrails & Operating Contract — 19 points, as
   amended by the owner (see docs/05).
5. The Universal Windows Desktop Master Prompt — Windows-specific
   supporting detail.
6. The project's own rule sheet (its Appendix 7 instantiation).

## Non-negotiables

1. **Classify before building.** Every project declares its tier
   (t1a–t5) in a `.project-tier` file and a Project Manifest block;
   the tier's rules are inert outside that tier.
2. **Everything is an operation.** A feature is implemented first as
   an operation/command callable identically from GUI, CLI, and any
   other surface. No GUI-only features.
3. **The gate is hard.** `QUALITY.md` scored from evidence; any Fail
   dimension means not done. Coverage floors: 85% core, 70% overall,
   100% on safety paths. Certainty ≥95% before building, 100% on
   irreversible or security-relevant choices — below that, ask with
   described options.
4. **No new external dependency without the owner's explicit
   approval**, plus a licence check, a register entry, and an exit
   sketch. Prefer the standard library and platform APIs.
5. **Zero cloud, zero telemetry.** Programs work fully offline;
   the one allowed network touch is an optional, switch-off-able
   update check that offers and never forces.
6. **One release shape.** `AppName-v{VERSION}-x64-Setup.exe` +
   `AppName-v{VERSION}-x64-Portable.zip` + `SHA256SUMS.txt`. No
   MSI, no other architectures, no bare exes. Packaged with SeanPak,
   themed with TesselGUI, unless the owner exempts the project.
7. **Never winget.** No code-signing certificate exists; binaries
   ship unsigned and the docs say so. Never propose winget.
8. **Merges, tags, and releases need the owner's explicit say-so
   for that instance.** Local commits and feature-branch work
   proceed freely. Batch publishes into the fewest operations.
9. **Never lose the user's work.** Autosave; destructive actions
   get undo, a backup, or a preview first. Config files carry a
   `schema_version` with tested upward migrations.
10. **Public docs are product facts only.** No references to the
    owner, briefs, or process. READMEs open with `## TL;DR` and use
    only real screenshots from the owner's machine.
11. **Report honestly.** Label claims Verified / Partially Verified
    / Unverified. Runtime that only the owner's machine can prove
    is recorded Unverified — never ask the owner to field-test.
12. **Pause means pause.** A pause/stop on a project halts all work
    on it until the owner says resume; leave a clean state and a
    summary. Pauses are per-project and literal.

# 01 — The system at a glance

Five layers, one direction of authority: a higher layer wins on
conflict unless the owner says otherwise in the moment.

| # | Layer | Decides |
|---|---|---|
| 1 | The owner's current instruction | This task, this instance — including one-off exemptions |
| 2 | Elite Software Master Prompt | How software is conceived and judged: benchmark-first, operations, quality gate, certainty, budgets, honesty |
| 3 | Adaptive Engineering Contract V4.0 | What a project is (tier), what it may be built with (stacks), the universals, the release matrix |
| 4 | AI Coding Guardrails | How the work itself is conducted: dependencies, secrets, testing, failure stops, reporting |
| 5 | Windows Desktop Master Prompt | Windows-specific craft: UX, accessibility, safety protocols, evidence labels |
| 6 | The project's rule sheet | This project's instantiation: purpose, frozen foundation, build/gate commands, budgets, special rules |

## How a project adopts the system

- **New projects** are under the system from day one: the rule sheet
  is created at project start, the tier is declared, the standard
  documents are seeded (docs/10).
- **Existing projects** adopt the project-level artefacts (rule
  sheet, `QUALITY.md`, `docs/PARITY.md`) at their next substantial
  slice or major version. Never retrofit a shipped project
  mid-release.
- **Abandoned and paused projects** are untouched until the owner
  resumes them.
- **Exemptions are explicit.** The owner may exempt a project from a
  layer's piece (for example a design-system exemption with an
  approved alternative look). An exemption is recorded in the
  project's rule sheet and never assumed from silence.

## Activation, for substantial work

Before building anything substantial, the helper:

1. Restates the brief in its own words.
2. States its certainty against the floors in docs/04.
3. Surfaces missing fields as decisions — multiple described
   options with trade-offs and a recommendation, never a single
   take-it-or-leave-it.
4. Classifies the project (tier + rationale) and checks the stack
   against docs/02 before writing code.

## What the system optimizes for

Software that is free, offline, dependable, and pleasant in the
first minute; releases that are few, grouped, and verified; and an
owner who directs in short bursts without wading through approval
prompts — because publishing is batched and the irreversible steps
(merge, tag, release, permanent delete) are the only ones that wait
for a say-so.

# 02 — Tiers and stacks

Every project is classified into exactly one tier. Classification is
autonomous: inspect the project's files, declare the tier and the
rationale, and record both durably — a `.project-tier` file plus a
`## Project Manifest` block in the repo. Ask the owner only when the
evidence genuinely contradicts itself.

## The tiers

| Tier | What it is | Release shape |
|---|---|---|
| t1a | Headless daemons and services | Setup.exe + Portable.zip + SHA256SUMS.txt |
| t1b | GUI / tray utilities | Setup.exe + Portable.zip + SHA256SUMS.txt |
| t2 | CLI tools and libraries | Per-target-triple zips + SHA256SUMS.txt |
| t3 | Rich-render desktop apps | Setup.exe + Portable.zip + SHA256SUMS.txt |
| t4 | WoW addons | Addon zip + SHA256SUMS.txt (see the WowDev repo for t4 craft) |
| t5 | Android apps | apk / aab + SHA256SUMS.txt (see the GodotDevTools repo for the Godot route) |

Tier rules are inert outside their tier: a t2 library does not carry
t1b tray rules, and a t4 addon follows its platform's own format
rules where those mandate placement or shape.

## Primary stack

**Rust with `windows-sys`, or C++20/MSVC with a static CRT** —
native Win32 / Common Controls v6, Slint, or Direct2D for UI;
event-driven (no polling), low-priority workers, bounded caches,
raw Win32 preferred over heavy wrappers; RAII handle management;
native tray, theme, DPI, and single-instance (GUID mutex) handling.

Rust release profile: `opt-level` z or s, `lto`, `codegen-units = 1`,
`panic = abort`, stripped. `unwrap`/`expect` are banned in hot paths
and untrusted-input code; justified exceptions live in main/tests
only.

## Sanctioned alternates (hard publish constraints)

An alternate is compliant only inside its constraints:

| Alternate | Constraints |
|---|---|
| C# / .NET | Self-contained **single-file** publish only; never framework-dependent |
| WinUI 3 | **Banned** |
| Tauri 2.x | System WebView2 only; no remote content |
| Flutter | `windows-release` builds only |
| Python | Nuitka-compiled only |
| PowerShell | Compiled XAML form only |

A stack the owner specifies directly in a project brief supersedes
the default for that project (an Electron app briefed as Electron
ships as Electron). Record the deviation in the project's rule
sheet.

## Budgets (Class A — the owner confirms changes in-session)

- RAM: under 15 MB for t1a; under 40 MB for t1b/t3 — each with a
  stated measurement basis in the project docs.
- Per-stack RAM budgets apply to the alternates as recorded in the
  contract's classification companion.
- Performance regressions over 10% in a core workflow block a
  release unless waived in writing with a follow-up.

# 03 — The engineering contract (V4.0 distilled)

## Universal mandates (all tiers)

- **Zero cloud, zero telemetry.** Programs function air-gapped. The
  single allowed network behavior is an optional update check that
  offers, never forces, and can be switched off (docs/06).
- **Respect the user.** No nagging, no dark patterns, no selling
  data. Software is completely free; optional donations never
  unlock anything.
- **Config carries `schema_version`.** Every config file declares
  its schema version and ships explicit, tested upward migrations —
  a CI migration fixture per version bump. A failed migration backs
  up and quarantines; it never silently discards user data.
- **Atomic writes** for anything the user would miss; DPAPI for
  sensitive data at rest on Windows; WAL/checkpoint-style recovery
  where a store can be interrupted.
- **Validate all input.** Malformed user data is quarantined and
  reported, never silently dropped and never a crash.
- **Local structured logs only.** Nothing leaves the machine.

## Override classes — who may bend what

| Class | Covers | Who decides |
|---|---|---|
| A | Numeric caps (RAM, budgets) and stack choices | The owner, in-session, explicitly |
| B | Style and tooling preferences | The helper, self-serve |
| C | The universals above | Never violated silently by an agent; the owner changes them only by amending the contract |

## The release matrix (as amended)

Every desktop release (t1a/t1b/t3) ships exactly:

- `AppName-v{VERSION}-x64-Setup.exe`
- `AppName-v{VERSION}-x64-Portable.zip`
- `SHA256SUMS.txt`

No `.msi` — ever, at any tier. No x86 or ARM64 variants. t2 ships
per-target-triple zips, t4 the addon zip, t5 apk/aab — each still
with `SHA256SUMS.txt`. All desktop installers are built by SeanPak
(docs/08). t1a/t1b programs support `--clean` / `--uninstall`
alongside the standard flag set (`--headless`, `--json`, `--silent`,
`--dry-run`, `--verbose`, `--debug`, `--trace` where they apply).

# 04 — Quality gates (the Elite Prompt distilled)

## Benchmark first

Before designing, study what the leading programs in the category
do. If the plan is missing a capability every leader has, flag it
with an Include / Defer / Reject recommendation. Benchmarking is an
internal step; public docs never carry competitor comparisons.

## Everything is an operation

Each capability is implemented once, as an operation (command) in a
registry, and every surface — window, CLI, JSON channel, scripting —
dispatches to it. A feature that exists only inside a click handler
is a defect (failure mode 7 below): untestable, unscriptable,
unreusable.

## The QUALITY.md gate

Every substantial project keeps a `QUALITY.md`, scored from
evidence, never from impressions:

- Any dimension scored **Fail** means the work is **not done**.
- Overall score must reach **85**, with **no dimension under 3**.
- A fresh-context adversarial pass reviews what the builder built;
  the builder is never the sole reviewer of their own work.
- A missed budget is recorded as a **waiver** with a reason and a
  follow-up — thresholds are never quietly edited. Minor waivers
  the helper may grant; major ones need the owner.

## Coverage and certainty floors

- Coverage: **85%** of core logic, **70%** overall, **100%** of
  safety paths (destructive actions, migrations, parsing of
  untrusted input).
- Certainty: **≥95%** overall before building; **100%** on
  irreversible or security-relevant choices. Below the floor, stop
  and present described options.
- The gate is the **full** gate: all tests, all targets, output
  actually read. A filtered subset presented as a gate is failure
  mode 5.

## The failure modes the gate exists to catch

| # | Mode | Catch |
|---|---|---|
| 1 | Demo-ware | A polished slice hiding an unfinished core |
| 2 | Happy-path only | No error/empty/offline states; tests that never fail anything |
| 3 | Silent scope narrowing | A requirement quietly reinterpreted into something easier |
| 4 | Invented API or fact | A call, flag, or claim no source supports |
| 5 | Filtered gate | Only some tests run before merge/release |
| 6 | Self-graded homework | Builder as sole reviewer; scores without evidence |
| 7 | GUI-only feature | Capability trapped in a UI handler |
| 8 | God function / god file | One unit doing everything |
| 9 | Copy-paste twins | Same logic in two places, drifting |
| 10 | Silent data loss | Parse failure discards; migration overwrites the original |
| 11 | Swallowed errors | Empty catches; "success" reported on failure |
| 12 | Unbounded work | No limits on loops, caches, retries, polling |
| 13 | Secret in the open | Key, token, or personal data in code, logs, or docs |
| 14 | Dependency by default | A library added "because everyone uses it" |
| 15 | Novelty over native | A custom control where a standard one exists |

## PARITY.md

Substantial projects keep `docs/PARITY.md`: the capability matrix
against the category leaders, scored only from test and corpus
evidence. The test corpus grows with every slice.

# 05 — Guardrails (the 19-point contract, as adopted)

The owner's AI Coding Guardrails & Operating Contract, adopted
exactly as written, with three overrides the owner chose explicitly.
The points, in operative form:

1. **No unvetted dependencies** — and per override (3) below, every
   new external dependency needs the owner's explicit approval
   before introduction.
2. **Follow existing patterns** in the codebase before inventing new
   ones.
3. **Zero secrets** in code, logs, docs, or commits.
4. **Default-deny** for auth and data access.
5. **Test-driven, checkable verification** — claims carry evidence.
6. **No `unwrap`/`expect`** (or their equivalents) in production
   paths.
7. **Three-strike failure stop** — after three failed attempts at
   the same approach, stop, reassess, and change route instead of
   persisting. (A proven route beats a fifth retry of a failing
   one.)
8. **Human gate for destructive actions** — deletes, overwrites,
   and system changes are confirmed first; permanent deletes always
   ask, and any "stop asking" preference is its own separate,
   described decision.
9. **Fresh context for distinct tasks** — don't let one task's
   assumptions leak into another.
10. **Living documentation** — docs change in the same change as the
    thing they describe.
11. **No unrequested refactoring.**
12. **Surgical diffs** — the smallest change that does the job.
13. **Complete files for new code** — no placeholder stubs shipped
    as finished.
14. **Readiness verification** before initializing or resuming a
    project: check scope, current code, live remote state, and
    pending approvals first.
15. **Documentation synchronization per release** — README, About,
    topics, and docs re-checked at every release (docs/09).
16. **Competitive feature integration without bloat** — adopt what
    leaders prove valuable; refuse feature creep.
17. **Concise reporting** — what was done and why, in as few words
    as possible.
18. **Progress on every task** — per override (2) below.
19. **Execution velocity** — keep moving; use waiting time on the
    next slice's preparation instead of idling.

## The owner's three overrides

1. **Git autonomy, with a gate.** Commit, pull, branch, and publish
   mechanics proceed without asking. **Merging, tagging, and
   cutting a release each need the owner's explicit say-so for that
   instance** (2026-11-13, superseding the earlier full-autonomy
   grant for those three steps).
2. **Progress % and an estimate on every active task**, even when
   the estimate is rough — plus a progress update every 5 minutes
   during any long-running job.
3. **Dependency approval.** Every new external dependency needs the
   owner's explicit approval before it is introduced, on top of
   the Elite Prompt's justify/register/exit-sketch duties.

# 06 — Every-program rules

These apply to every Windows program in the family, whatever its
tier or stack.

## Capability and continuity

- **Full command-line support.** Every capability available in the
  window is usable from the command line (the CLI dispatches to the
  same operations — docs/04).
- **Never lose the user's work.** Programs save as the user goes,
  quietly and without being asked. After a crash or power cut,
  reopening restores the work exactly where it was left.
- **Reopen where they left off.** Last file, place, geometry, and
  settings restored (window geometry validated against the actual
  monitors); a short recent-items list.
- **Undo for anything destructive.** Delete, overwrite, or
  important change → undo, a backup copy first, or a preview with
  confirmation. Nobody ruins something with one wrong click.

## First minute and everyday use

- **Useful in the first minute.** The main job is doable within a
  minute of first opening: sensible defaults, no setup forms or
  account demands in the way.
- **Search wherever there's lots of stuff.** Many settings, files,
  or items → a search box.
- **Help inside the program.** A short plain-words guide (Help
  button or F1), fully offline.
- **Drag and drop.** File programs accept drops onto the window.
- **Audience-first.** Design for the program's actual users and
  situations; safe defaults for beginners, grouped and explained
  advanced controls for pros.

## Interface craft

- **Per-Monitor DPI v2 aware.** All spacing, padding, fonts, and
  control sizes scale with the DPI factor — relative units, never
  static pixels. Fluid layouts; a sensible minimum size below which
  secondary content clips, scrolls, or collapses instead of
  overlapping core controls. Text wraps or truncates cleanly with
  ellipsis. Icons are vector/scalable. Spacing follows a 4px/8px
  grid. Every interactive element has explicit hover, pressed,
  focused, disabled, and loading states. Test the extremes:
  minimum size, ultrawide/4K, 100%–300%+ scaling.
- **No primary-window scrollbars** — scrolling lives in virtualized
  lists. Real-time status where work happens (bytes, rate,
  progress), with fast cancellation.
- **Standard controls first**; a custom control must justify itself
  (docs/04, failure mode 15). Accessibility is required, not
  polish: keyboard paths, focus visibility, high-contrast survival.
- **Errors say what happened and how to fix it**, in plain words.

## Privileges and updates

- **No admin by default.** Programs run unelevated; when admin is
  genuinely required, the program explains why in plain words
  *before* asking.
- **Updates offered, never forced.** An optional update check (the
  one allowed network touch) may offer a newer version with a plain
  description of what's new. It never installs on its own, never
  nags after a "no", and can be switched off in settings.
- **No nagging, ever.** No review/rating/donation popups; a quiet
  donate link in the About box is the limit.

# 07 — Design: the TesselGUI system

Every program conforms to the latest **TesselGUI** — currently
v2.0.0 revision 3, the **Carmine** scheme — unless the owner exempts
the project in writing (an exemption is recorded in the project's
rule sheet, with its approved alternative).

## Carmine in brief

- Dark charcoal, near-black surfaces: editor `#1B1B1D`, panels
  `#232326`. Text `#E6E3E1` on them, muted text `#89868A`.
- **Carmine accent `#960018`** — used for action, focus, and
  selection, and **never as the only cue** (pair it with shape,
  position, or text so meaning survives color blindness and high
  contrast).
- A fine square grid texture (`#28282B`) on the main window.
- Compact-first density; Consolas-first type for code and data.
- The GitHub scheme survives as a preset; light mode takes the
  Carmine family; High Contrast is its own scheme and is unchanged
  by rethemes.

The full token set is in
[reference/tesselgui-carmine-tokens.md](../reference/tesselgui-carmine-tokens.md);
the machine-readable source of truth is `docs/tokens.json` in the
TesselGUI repo — check there for anything newer.

## Layout and interaction rules

- The responsive rules of docs/06 (DPI scaling, 4/8px grid, fluid
  containers, all control states) are part of conformance, not
  taste.
- **Scoped tooltips:** required on icon-only buttons, non-standard
  custom controls, status indicators, and column headers.
  Self-describing labeled buttons do not get redundant tooltips.
  (This scoping superseded an earlier tooltips-on-everything rule
  in 2026-11.)
- **The mockup gate:** design confirmation is required only for a
  new top-level window or a layout change bigger than a single
  dialog/menu. Mockups are shown as images.

## Conformance timing

New projects conform from day one. Existing projects adopt the
current TesselGUI at their next slice or release — a retheme is a
slice of its own, batched with that project's pending work, never a
drive-by edit inside another change.

# 08 — Packaging with SeanPak

Every Windows program release is packaged with **SeanPak** — the
per-project installer scripts (NSIS, Inno, hand-rolled WiX) are
retired as a packaging route. A project's release workflow calls
SeanPak; it does not build its own installer.

## The pipeline

Manifest + payload files in → three assets out:

- `AppName-v{VERSION}-x64-Setup.exe`
- `AppName-v{VERSION}-x64-Portable.zip`
- `SHA256SUMS.txt`

SeanPak's primary user is the build pipeline itself: the headless
route (`seanpak pack` with `--json`, `--silent`, `--dry-run`) is
the main workflow, with deterministic exit codes and a JSON report;
the Builder GUI is secondary. Full CLI parity applies to SeanPak
like everything else (docs/06).

## The manifest

Each project carries a `seanpak.json`: app identity, version,
payload layout, install location token, and options. A starter is
in [templates/seanpak-template.json](../templates/seanpak-template.json).
Version strings live in more places than the manifest (project
build props, a program constant) — a version bump updates **every**
copy, and the release checklist (checklists/release-checklist.md)
asks for each one by name.

## Install behavior (owner's directives)

- **Per-user by default.** The default install location is the
  per-user Programs folder (`%LOCALAPPDATA%\Programs\<App>`),
  never Program Files. Writability is checked before anything
  changes; if the chosen folder is not writable, the per-user
  location is offered as fallback — never a silent elevation.
- Desktop icon by default; "launch after setup" ticked by default.
- **Silent auto-update when already installed:** a newer installer
  run over an existing install updates in place, closing and
  relaunching running instances; only a process that refuses to
  close interrupts, once.
- The installer enforces a declared Windows-version floor, packs
  declared Microsoft redistributable prerequisites at build time
  (never downloaded at install time — zero cloud), and offers
  repair through Modify/uninstall.
- Portable installs are a first-class choice, including an
  `extract` command that unpacks without installing.

## Verify before calling it shipped

`seanpak verify` plus the read-back discipline of docs/09: assets
re-downloaded, hashes matched against `SHA256SUMS.txt`, and any
hand-built binary PE-import-checked (system DLLs only) before it is
attached to a release.

# 09 — Release and verification

## The shape (no exceptions without the owner's word)

Exactly three assets per desktop release:

- `AppName-v{VERSION}-x64-Setup.exe`
- `AppName-v{VERSION}-x64-Portable.zip`
- `SHA256SUMS.txt`

x64 only. No MSI, no ARM64/x86 variants, no PortableApps zips, no
bare loose exes. Distribution is GitHub Releases only — **never
winget** (no code-signing certificate exists; binaries ship
unsigned and the release notes say so honestly).

## Cadence

- **Grouped releases.** Small fixes accumulate on main and ship
  together in the next grouped release; a fix does not get its own
  version.
- **Substantial PRs only.** Batch related work into one substantial
  pull request; trivial changes ride the next batch.
- **The gate before the release:** merges, tags, and releases each
  need the owner's explicit say-so for that instance (docs/05).
  Work that reaches a publish step without it holds there and
  reports ready.
- **Batch the publish.** One batched push per publish wherever it
  fits; everything else (PRs, merges, branch ops) through the
  signed-in browser. Never loop per-file writes.

## Verification (all of it, every time)

1. The **full gate** ran locally first — all tests, all targets,
   output read (docs/04). CI confirms; it does not substitute.
2. Published files are **read back** and compared by git blob SHA
   (byte-identity), not by eyeballing rendered pages.
3. Release assets are **re-downloaded** after upload and matched
   against `SHA256SUMS.txt`.
4. Any binary built outside the proven CI route is
   **PE-import-checked**: its imports must be system DLLs only. A
   hash match alone has shipped a broken binary before — hash
   proves identity, not loadability. Tauri release assets come
   from the MSVC CI route, never a local cross-build; Electron
   Windows releases likewise ship from the Windows CI workflow.
5. **Release documentation sync:** the release carries only that
   version's own changelog section; README, repo description, and
   topics are re-checked for accuracy against what shipped, and
   screenshots are refreshed from real captures (owed captures are
   flagged, never faked).

## Honest labels

Every claim in a release report is labeled **Verified**,
**Partially Verified**, or **Unverified**. Windows runtime behavior
that was not exercised stays Unverified — recorded plainly, never
smoothed over, and never turned into a request for the owner to
field-test.

# 10 — Project lifecycle

## Storytold orchestration (how parallel work runs)

1. **Foundation freeze first.** Module layout, layering, and
   interfaces are frozen and written into the repo before any
   parallel work starts. An interface change lands alone, first.
2. **Swarm: 6–8 agents maximum**, one directory each, working from
   the standard brief. Workers never commit, push, or open PRs.
3. **The integrator merges serially**, personally running the FULL
   gate on each worktree and again on the merged tree.
4. Every substantial project keeps `docs/PARITY.md` and a test
   corpus that grows per slice (docs/04).

New projects run this way from day one; existing projects adopt it
at their next substantial slice or major version.

## The standard document set

Every project carries the files from the standard set that
genuinely apply — 17 in `docs/`, plus `README.md` and `LICENSE.md`
at the root (never duplicated in both places). The full list and
its rules are in
[reference/standard-docs-set.md](../reference/standard-docs-set.md).
Real content only; platform-mandated placement (a WoW addon's root
files, a PortableApps layout) wins over the set.

## Repo rules

- Every repo gets its **About description and topics** filled at
  creation, and re-checked at every release (docs/09).
- **README** opens with `## TL;DR` in plain words, then features,
  real screenshots, requirements from evidence, install steps,
  usage, configuration, build instructions, troubleshooting for
  real known errors, and honest limitations. Anything undetermined
  is written "To be confirmed" — never guessed.
- **MIT by default** for the owner's projects, unless a different
  license is recommended for a specific project and the owner
  agrees.
- Public docs contain factual product documentation only — no
  references to the owner, briefs, or design process, and no
  competitor comparisons by default.

## Slices, pauses, and stops

- Plan **fewer, larger combined slices**: one slice carries
  everything that belongs together.
- **Local first** whenever local is faster — builds, tests, gates,
  packaging prep. GitHub is for hosting, PRs, releases, and what
  local cannot genuinely produce.
- **Pause protocol:** when the owner says pause/stop on a project,
  stop — no changes, commits, or PRs until an explicit resume.
  Leave the work clean and safe, and hand over a summary: what is
  completed, what is in progress, any uncommitted changes, and the
  next steps. Pauses are literal and per-project; one project's
  pause never bleeds into another's, and an abandoned project is
  never revived or re-suggested without the owner's word.

# Stack decision table

One page: what you're building → the sanctioned route. Detail and
constraints live in [docs/02](../docs/02-tiers-and-stacks.md).

| Building | Tier | Default route | Alternates (constrained) |
|---|---|---|---|
| Background service / daemon | t1a | Rust (`windows-sys`), static CRT | C++20/MSVC |
| Tray or small GUI utility | t1b | Rust + native Win32/Slint | C# single-file publish; Tauri 2.x on system WebView2 |
| CLI tool or library | t2 | Rust | C++20; PowerShell (compiled XAML form for any UI) |
| Rich-render app (canvas, media, complex views) | t3 | Rust + Direct2D/Slint | Flutter `windows-release`; Tauri 2.x (system WebView2, no remote content) |
| WoW addon | t4 | Lua 5.1 subset against the target client's API — see the WowDev repo | — |
| Android app/game | t5 | The project's engine route — for Godot, see the GodotDevTools repo | Native Kotlin/Compose for non-game apps |

Hard rules that cut across the table:

- **WinUI 3 is banned.** Python ships only Nuitka-compiled. .NET
  ships only as a self-contained single file.
- A stack named directly in the owner's project brief supersedes
  this table for that project; record the deviation in the project
  rule sheet.
- Every desktop tier packages with SeanPak and (unless exempted)
  themes with TesselGUI.

# The standard document set

Every project carries the files from this set **that genuinely
apply to it** — real content only, no placeholders, no invented
facts. Public docs hold factual product documentation only.

## In `docs/` (on main)

`AUDIT.md` · `CHANGELOG.md` · `FEATURES.md` · `COMPATIBILITY.md` ·
`ROADMAP.md` · `BENCHMARK.md` · `CREDITS.md` · `CONTRIBUTING.md` ·
`CODE_OF_CONDUCT.md` · `SUPPORT.md` · `SECURITY.md` ·
`MAINTAINERS.md` · `GOVERNANCE.md` · `ARCHITECTURE.md` ·
`TROUBLESHOOTING.md` · `INSTALL.md` · `MIGRATION.md`

## At the repo root

`README.md` · `LICENSE.md`

Root placement is deliberate: GitHub only detects a license at the
root, and the root README is the repo's face. Never keep duplicate
copies of a file in both places — they drift.

## Rules

- Only files that genuinely apply ship. No `MIGRATION.md` where
  nothing has ever migrated; no `BENCHMARK.md` where nothing is
  measured.
- Where a platform format mandates its own placement (WoW addon
  root files, a PortableApps tree), the format wins.
- Files a project already keeps at its root (`CHANGELOG.md`,
  `FEATURES.md`, `ROADMAP.md`, …) move into `docs/` when the
  project adopts the standard, with inbound links updated.

## Rollout

New projects from day one; existing active projects at their next
slice or publish (no mid-release retrofit); abandoned and paused
projects untouched.

# Release checklist

One release = one grouped batch (docs/09). Nothing here is
optional without a recorded waiver.

## Gate
