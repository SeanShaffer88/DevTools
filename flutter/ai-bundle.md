# AGENTS.md — Instructions for AI agents writing Flutter code

You are using this pack as your knowledge base for creating Flutter
and Dart apps. Follow these rules exactly.

## Non-negotiable rules

1. **Never invent package names, versions, or APIs.** Every package
   you add and every version you pin must be traceable to its page on
   **pub.dev**; every Flutter/Dart API to **docs.flutter.dev** or
   **api.flutter.dev** / **dart.dev**. If you cannot trace it, do not
   write it — say it is **Unverified** instead. Versions in this pack
   (including [reference/dependencies.md](reference/dependencies.md))
   are a dated snapshot: re-check pub.dev before pinning, because
   Flutter-ecosystem packages release monthly.
2. **State the target platform first.** Before writing code, name the
   target: Android, Windows, web, iOS, macOS, Linux — and the build
   mode where it matters. Platform decides the APIs, the plugins, the
   build command, and the distribution shape. Remember: desktop apps
   build only on their own OS (a Windows app builds on Windows), and
   performance is measured in **profile mode on a real device**, never
   debug ([guides/13](guides/13-performance-and-devtools.md)).
3. **Null safety, always.** All Dart code is sound null-safe. No
   opting out, no `// @dart=2.9`, no sprinkling `!` to silence the
   analyser — model absence honestly (nullable types, sealed states)
   and fix the model when the analyser complains.
4. **Do not use the original `hive` or `isar` packages in new
   projects.** Both are stale (hive last released 2022, isar 2023).
   Use the maintained successors named in
   [reference/dependencies.md](reference/dependencies.md) (`hive_ce`,
   `isar_community`, ObjectBox) — or, more often, **drift** or
   **shared_preferences**, which cover most apps' real needs
   ([guides/07](guides/07-local-storage.md)).
5. **`integration_test` comes from the SDK, never from pub.** It is
   declared as `sdk: flutter` in dev_dependencies. A version-pinned
   pub.dev copy of `integration_test` in a new project is a
   version mix-up.
6. **Respect the `material_ui` transition.** Flutter's Material
   library is being restructured (the `material_ui` effort). Prefer
   current Material 3 APIs as documented on docs.flutter.dev today,
   check for deprecations after every Flutter upgrade with
   `flutter analyze`, and do not copy Material 2 patterns from old
   tutorials into new code.
7. **AAB for Play, whole folder for desktop.** Android releases for
   Google Play are **Android App Bundles** signed through Play App
   Signing ([guides/10](guides/10-android-release.md)). Windows
   releases ship the **whole** `build\windows\x64\runner\Release\`
   folder (or an MSIX made from it), never the bare `.exe`
   ([guides/09](guides/09-windows-desktop.md)).
8. **No secrets in the repo.** No API keys beyond public client keys,
   no keystores or their passwords, no service-account JSON, no
   signing material. Signing config reads from a git-ignored
   `key.properties` / environment. `--dart-define` values are
   compile-time constants visible in the binary — configuration, not
   secrecy ([guides/12](guides/12-flavors-and-config.md)).
9. **Community packages are community packages.** window_manager,
   tray_manager, and friends are third-party work, however popular.
   Say so when you recommend one, check its maintenance on pub.dev,
   and keep platform-plugin calls behind platform checks and your
   composition root.
10. **Verify before declaring done.** Run, in this order:
    `dart format`, `flutter analyze` (clean), the test suite
    (`flutter test`), and a build for the target platform. State
    plainly which of these ran and which could not — label the rest
    **Unverified** rather than claiming success. Code that has never
    compiled is not done.

## Build order (always in this sequence)

1. Name the target platform(s) and form factor (rule 2).
2. Scaffold or open the project; confirm `flutter doctor` is clean
   for the target toolchain and a debug run works
   ([guides/01](guides/01-getting-started-and-toolchain.md)).
3. Set the lint baseline (flutter_lints) and folder structure
   ([guides/14](guides/14-architecture-and-project-structure.md)).
4. Build the smallest end-to-end slice: one screen, real data path,
   one repository.
5. Add state management, routing, storage, and networking as the
   feature list actually needs them — not before
   ([guides/04](guides/04-state-management.md)–[07](guides/07-local-storage.md)).
6. Test as you go (unit → widget → golden → integration,
   [guides/08](guides/08-testing.md)); profile in profile mode before
   optimising anything.
7. Release per platform: AAB + Play tracks for Android, Release
   folder/MSIX for Windows ([guides/09](guides/09-windows-desktop.md),
   [guides/10](guides/10-android-release.md)).

## Things that are always wrong

- A package version, plugin, or API that appears in no pub.dev /
  official-docs source for the stated Flutter version.
- Original `hive` / `isar`, or a pub-pinned `integration_test`, in a
  new project.
- Performance conclusions drawn from a debug build or an emulator.
- A Play upload built as a raw APK instead of an AAB.
- Shipping a Windows `.exe` without its engine DLL and `data\` folder.
- Signing keys, keystores, or passwords committed to version control.
- Material 2-era patterns copied from old tutorials into new code.
- Reaching for a state-management/framework package before the app's
  size justifies it.
- Treating a blog post, video, or model memory as proof a package
  version or Play policy is current — re-check pub.dev / official
  sources.

# 01 — Getting Started and the Toolchain

Flutter is Google's UI toolkit for building apps for Android, iOS,
Windows, macOS, Linux, and the web from one Dart codebase. This guide
gets a Windows machine from nothing to a running app, and explains
how to keep the toolchain pinned, healthy, and up to date.

Official starting point: https://docs.flutter.dev/get-started/install

## The versions in this guide

- **Flutter 3.50.0 stable** (released 2026-11-11) — this is the SDK
  version everything here assumes.
- **Dart 3.14.0** is the Dart version *bundled inside* Flutter 3.50.0.
- **Standalone Dart is 3.14.1** — that is a separate download for
  server/CLI Dart. Do not confuse the two numbers: inside a Flutter
  project you always use the Dart that came with Flutter, never a
  separately installed Dart.

Check what you actually have at any time:

```powershell
flutter --version
dart --version   # only meaningful inside / via the Flutter SDK
```

## Channels: which Flutter you are tracking

Flutter ships on channels, which are just git branches of the SDK:

| Channel | Cadence | Use it for |
|---|---|---|
| `stable` | Quarterly releases | Almost everyone, almost always |
| `beta` | Monthly | Previewing the next stable, CI early-warning |
| `main` | Continuous | Flutter contributors, checking if a bug is already fixed |

Switch and upgrade with:

```powershell
flutter channel stable
flutter upgrade
```

Stay on `stable` unless you have a named reason not to. A bug that
only reproduces on `beta` or `main` is a preview bug, not your app's
bug yet.

## Install route 1 (recommended): VS Code

On Windows this is the route the Flutter team recommends:

1. Install Visual Studio Code.
2. Install the **Flutter extension** for VS Code (it brings the Dart
   extension with it).
3. Open the Command Palette (`Ctrl+Shift+P`) and run
   **Flutter: New Project**. VS Code will offer to locate or download
   the Flutter SDK for you — accept, and pick a permanent home for
   it, for example `C:\dev\flutter`.
4. Let the extension add the SDK to your `PATH` when it asks.

Why this route wins: the extension handles SDK placement, PATH, and
first-run prompts, and it is the setup the official docs test first.

## Install route 2: manual SDK zip

1. Download the Flutter SDK zip for the current stable from
   https://docs.flutter.dev/get-started/install/windows — there is
   **no MSI installer**; anyone offering one is not official.
2. Unzip it to a folder you own, e.g. `C:\dev\flutter`.
   - Do **not** put it in `C:\Program Files` (permission prompts).
   - Do **not** put it in a path with spaces if you can avoid it.
   - Avoid very deep paths: Windows long-path limits bite Flutter
     builds. Keep the SDK and your projects on short paths such as
     `C:\dev\...`.
3. Add `C:\dev\flutter\bin` to your user `PATH`.
4. Open a **new** terminal and run `flutter doctor` (below).

## Pinning an exact SDK version

The Flutter SDK is a git checkout, so a version is a commit:

```powershell
cd C:\dev\flutter
git fetch
git checkout 3.50.0      # the tag for Flutter 3.50.0 stable
flutter doctor
```

Teams that need every machine and CI runner on the same Flutter
should pin this way (or with a version-manager tool) instead of
letting each developer float on "latest stable". Record the pinned
version in the project readme. `flutter upgrade` moves you forward
again when you deliberately unpin.

## flutter doctor: the health check

`flutter doctor` is the single most important command in Flutter.
It checks every target you might build for and tells you, in plain
text, what is missing. Run it verbosely when something looks wrong:

```powershell
flutter doctor -v
```

Work through it target by target — you only need the targets you
actually ship to.

### For Android

You need, all from Android Studio's SDK Manager:

- Android Studio itself (it provides the SDK manager and emulator UI)
- **SDK Platform for API 36** (the current compile target)
- Android SDK Command-line Tools (latest)
- Android Emulator
- Android SDK Platform-Tools (`adb` lives here)
- CMake
- NDK (Side by side)

Then accept the licences and verify:

```powershell
flutter doctor --android-licenses
flutter doctor
```

Create an emulator in Android Studio's Device Manager, or check

```powershell
flutter emulators

```

### For Windows desktop

Windows desktop builds are native C++ under the hood, so you need:

- **Visual Studio** (the full IDE, not just VS Code) with the
  **"Desktop development with C++"** workload installed.

That one workload is the whole requirement — without it, `flutter

### For the web

A current Chrome is enough for development. No extra SDK is needed.

## Your first app

```powershell
flutter create my_app
cd my_app
flutter run
```

Useful flags while learning:

```powershell
flutter run -d windows    # pick the target explicitly
flutter run -d chrome
flutter devices           # list everything you can run on
```

Inside a running app: `r` = hot reload (keep state, apply code),

## Keeping the toolchain healthy

- Run `flutter doctor` after every SDK, Android Studio, or Visual
  Studio update.
- Run `flutter pub get` after changing `pubspec.yaml` or switching
  branches — stale `.dart_tool` state causes confusing errors.
- `flutter clean` deletes build output and forces a full rebuild.
  It fixes a surprising share of "impossible" build errors.
- Upgrade on purpose, on `stable`, and read the release notes at
  https://docs.flutter.dev/release/release-notes before you do —
  then run your tests before committing the upgrade.

# 02 — The Dart Language for Flutter Developers

You do not need to master all of Dart before writing Flutter, but
these are the parts you will use every day. This guide assumes
Flutter 3.50.0, which bundles **Dart 3.14.0**.

Language tour: https://dart.dev/language
Effective Dart style: https://dart.dev/effective-dart

## The Dart 3 baseline

Dart 3 changed the ground rules. Code written for Flutter today:

- **Has sound null safety, always.** It cannot be disabled in
  Dart 3. A type is non-nullable unless you say otherwise with `?`.
- **Uses records, patterns, and exhaustive switches** (below) as
  ordinary tools, not novelties.
- **May use class modifiers** (`sealed`, `final`, `base`,
  `interface`, `mixin class`) to control inheritance.
- **May use primary constructors** (added in Dart 3.13) — a compact
  constructor syntax. You will meet it in newer code; the classic
  constructor syntax remains fully valid.
- **Does not use macros.** The Dart macros experiment was
  abandoned. Code generation in Dart means `build_runner` with
  generators such as `json_serializable` and `freezed` — see
  guide 06.

## Null safety in practice

```dart
String name = 'Ada';     // can never be null
String? nickname;        // may be null — and starts as null

int length = nickname?.length ?? 0;   // null-aware access + fallback
```

Rules of thumb:

- Prefer `?`, `?.`, and `??` over the bang operator `!`.
- `nickname!` means "crash if this is null". It is a promise you
  make to the compiler — make it rarely, and only when you have
  actually checked.
- `late` means "I will assign this before anyone reads it":

```dart
late final String config;   // assigned once during setup
```

Use `late` sparingly; a forgotten assignment is a runtime crash.

## Variables, types, and inference

```dart
var count = 0;            // inferred as int, then fixed as int
final title = 'Home';     // set once at runtime, cannot change
const maxItems = 100;     // compile-time constant

String greet(String who) => 'Hello, $who';   // string interpolation
```

`final` for almost everything local; `const` whenever a value is
known at compile time — `const` widgets in Flutter are a real
performance tool, not a style tic.

## Collections

```dart
final list = [1, 2, 3];
final set = {'a', 'b'};                    // no duplicates
final map = {'id': 1, 'name': 'Ada'};

final doubled = [for (final n in list) n * 2];       // collection-for
final maybe = [if (showExtra) 99];                   // collection-if
final copy = [...list, 4];                           // spread
```

Collection operators inside widget `children:` lists are the same
feature — Flutter UI code is full of `if` and `for` inside lists.

## Records: small anonymous data bundles

Records group a few values without declaring a class:

```dart
(String, int) parse(String s) => (s.trim(), s.length);

final (text, length) = parse(' hi ');   // destructure on receipt
```

Use a record for a private helper that returns two or three
related values. Use a real class when the data has a name, methods,
or a life outside one function.

## Patterns and exhaustive switch

Dart 3 pattern matching makes state handling in UI code much safer:

```dart
String describe(Object value) => switch (value) {
  int n when n < 0 => 'negative',
  int n => 'a number: $n',
  String s => 'text: $s',
  (String name, int age) => '$name is $age',   // record pattern
  _ => 'something else',
};
```

The key word is **exhaustive**: over a sealed type, the compiler
proves you handled every case, and adding a new case later turns
every unhandled switch into a compile error. That is exactly what
you want for UI states:

```dart
sealed class LoadState {}
final class Loading extends LoadState {}
final class Ready extends LoadState {
  Ready(this.items);
  final List<String> items;
}
final class Failed extends LoadState {
  Failed(this.message);
  final String message;
}

// In a widget:
switch (state) {
  Loading() => const CircularProgressIndicator(),
  Ready(items: final items) => ListView(children: [for (final i in items) Text(i)]),
  Failed(message: final m) => Text('Error: $m'),
}
```

## Classes and class modifiers

```dart
class Point {
  const Point(this.x, this.y);      // positional fields, const ctor
  final int x;
  final int y;

  Point.named({required this.x, required this.y});  // named ctor

  @override
  bool operator ==(Object other) =>
      other is Point && other.x == x && other.y == y;
  @override
  int get hashCode => Object.hash(x, y);
}
```

Modifiers you will actually use:

- `sealed class` — all subtypes live in the same library; enables
  exhaustive switching (above). The default choice for state types.
- `final class` — cannot be extended outside its library.
- `abstract class` — cannot be instantiated; a contract plus
  optional shared code.
- `mixin` — reusable behaviour mixed into classes with `with`.

Prefer composition and small sealed hierarchies over deep
inheritance trees.

## Functions

```dart
int add(int a, int b) => a + b;                       // arrow body
void log(String message, {bool verbose = false}) {}   // named params
void greet({required String name}) {}                 // required named

// Functions are values:
final names = ['ada', 'bo'].map((s) => s.toUpperCase()).toList();
```

In Flutter, callbacks are functions passed as values everywhere —
`onPressed: () => doThing()` is the pattern, not an exception.

## Async: Futures, Streams, isolates

A `Future<T>` is a value that arrives later. `async`/`await` is the
normal way to consume one:

```dart
Future<String> loadName() async {
  final response = await fetchFromSomewhere();
  return response.name;
}
```

A `Stream<T>` is many values over time — listen, or use Flutter's
`StreamBuilder`:

```dart
Stream<int> ticks() async* {
  var i = 0;
  while (true) {
    await Future<void>.delayed(const Duration(seconds: 1));
    yield ++i;
  }
}
```

Error handling is ordinary `try`/`catch`, including in async code:

```dart
try {
  final data = await load();
  show(data);
} on TimeoutException {
  showRetry();
} catch (e) {
  showError(e);
}
```

**Isolates** are Dart's separate memory/thread units — no shared
memory, messages only. Flutter runs your UI on the main isolate;
heavy parsing or computation (big JSON, image work) belongs on a
background isolate so the UI never janks:

```dart
final result = await Isolate.run(() => parseBigJson(rawText));
```

`Isolate.run` (and Flutter's older `compute`) is the easy path:
hand it a function and the input, get a Future of the output.

## What to skip for now

Generators beyond `async*` basics, extension types, FFI, and the
full modifier matrix can all wait until a real project needs them.
The features above — null safety, records, patterns, sealed
classes, collections, and async — are 95% of daily Flutter Dart.

# 03 — Widgets and UI

Everything on screen in Flutter is a widget — including layout,
padding, and even the app itself. Widgets are immutable
descriptions; Flutter compares new descriptions against the old
tree and updates only what changed.

Widgets catalog: https://docs.flutter.dev/reference/widgets
Layout guide: https://docs.flutter.dev/ui/layout

## The one mental model

> **Constraints go down. Sizes go up. The parent sets position.**

A parent passes constraints ("be between this wide and that
wide") to its children. Each child picks a size inside those
constraints. The parent then decides where the child sits. Almost
every layout surprise in Flutter is one of these three steps being
different from what you assumed — usually an *unbounded* constraint
(a scroll view inside a column is the classic).

## Stateless vs Stateful

A `StatelessWidget` is a pure function of its inputs:

```dart
class Greeting extends StatelessWidget {
  const Greeting({super.key, required this.name});
  final String name;

  @override
  Widget build(BuildContext context) {
    return Text('Hello, $name');
  }
}
```

A `StatefulWidget` owns mutable state that survives rebuilds:

```dart
class Counter extends StatefulWidget {
  const Counter({super.key});
  @override
  State<Counter> createState() => _CounterState();
}

class _CounterState extends State<Counter> {
  int _count = 0;

  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        Text('$_count'),
        ElevatedButton(
          onPressed: () => setState(() => _count++),
          child: const Text('Add'),
        ),
      ],
    );
  }
}
```

Why two classes? The widget object is recreated on every rebuild;
the `State` object is not. Configuration lives on the widget
(`widget.name`), mutable data lives in the state.

`setState` tells the framework "this state changed, rebuild me".
Call it for the change, never as a general refresh hammer — see
guide 04 for when to outgrow it.

## BuildContext

Every `build` receives a `BuildContext`. Think of it as the
widget's *location in the tree*: it is how a widget looks up
inherited services — theme, size, navigation, localization:

```dart
final theme = Theme.of(context);
final width = MediaQuery.sizeOf(context).width;
```

Rules that save hours:

- A context can only see **ancestors**, never descendants or
  siblings. "No Material widget found" and similar errors usually
  mean you used a context from *above* the widget that provides
  the thing.
- If you need a context below a provider, insert a `Builder` widget
  to get a fresh context at that point in the tree.
- Never store a context and use it after an `await` without
  checking `context.mounted` — the widget may be gone.

## Layout essentials

| Widget | What it does |
|---|---|
| `Column` / `Row` | Stack children vertically / horizontally |
| `Expanded` / `Flexible` | Share leftover space inside a Column/Row |
| `Padding` | Inset a child (prefer this over margin containers) |
| `SizedBox` | Fixed size, or a spacer with one dimension set |
| `Stack` + `Positioned` | Overlap children |
| `ListView` / `GridView` | Scrolling lists — use `.builder` for long ones |
| `ConstrainedBox` / `Align` / `Center` | Extra constraints / positioning |

```dart
Row(
  children: [
    const Icon(Icons.star),
    const SizedBox(width: 8),
    Expanded(child: Text(title, overflow: TextOverflow.ellipsis)),
    Text(price),
  ],
)
```

Always use `ListView.builder` (not a Column of children) for lists
whose length you do not control — builder creates rows lazily as
they scroll into view.

## Material, Cupertino — and the big 3.50 change

Flutter's design-system widgets historically shipped *inside* the
SDK: `import 'package:flutter/material.dart'` and
`package:flutter/cupertino.dart`. Most existing code, tutorials,
and packages still use those bundled imports, and they still work.

**Flutter 3.50 changes the direction.** The bundled Material and
Cupertino implementations are **deprecated in favour of standalone
packages**:

- `material_ui` — the Material implementation as its own package
- `cupertino_ui` — the Cupertino implementation as its own package

Both packages reached **1.0 in Flutter 3.47**, so they are not
experiments. The reason for the split: the design systems can now
be versioned and updated on pub.dev's schedule instead of waiting
for a quarterly Flutter release, and apps can pin a design system
independently of the framework.

How to act on this:

1. **Existing apps:** keep building. Run the automated migration
   when you adopt the new packages — `dart fix` applies the
   mechanical import/API updates.
2. **Use the compatibility bridge during migration:**
   `MaterialUiCompatibilityBridge` exists so an app can move
   incrementally instead of in one flag-day rewrite.
3. **New apps:** evaluate starting on `material_ui` /
   `cupertino_ui` directly, and say which choice the project made
   in its readme — mixed assumptions between bundled and package
   widgets are the failure mode to avoid.
4. **Learning:** learn concepts (scaffolds, buttons, dialogs,
   navigation) once — they carry across both. When a tutorial's
   imports differ from your project's, that is the split, not an
   error in the tutorial.

## Theming

Define the theme once at the app root; widgets read it through
`Theme.of(context)`:

```dart
MaterialApp(
  theme: ThemeData(
    colorScheme: ColorScheme.fromSeed(seedColor: Colors.teal),
    useMaterial3: true,
  ),
  darkTheme: ThemeData(
    colorScheme: ColorScheme.fromSeed(
      seedColor: Colors.teal,
      brightness: Brightness.dark,
    ),
    useMaterial3: true,
  ),
  home: const HomePage(),
)
```

`ColorScheme.fromSeed` generates a coherent Material 3 palette
from one colour. Prefer theme values (`colorScheme.primary`,
`textTheme.titleLarge`) over hard-coded colours and font sizes in
widgets — that is what makes dark mode and rebranding cheap.

## Responsive and adaptive

Responsive = the layout uses the space it has. Adaptive = the UI
also follows platform conventions. Start with the space:

```dart
LayoutBuilder(
  builder: (context, constraints) {
    if (constraints.maxWidth >= 700) {
      return const WideLayout();    // e.g. list + detail side by side
    }
    return const NarrowLayout();    // e.g. list only, tap to detail
  },
)
```

- Design breakpoints (for example ~600–700 logical pixels) around
  your content, not around named devices.
- On large screens, spend width on *more content at once*
  (two-pane layouts), not on stretched phone UI.
- Test with the window resized, not only on fixed emulator sizes —
  desktop and foldables change size at runtime.

## Performance habits that matter early

- Mark constructors `const` wherever possible; `const` widgets are
  reused instead of rebuilt.
- Keep `build` methods cheap and side-effect free — they run often.
- Split big widgets into small widget classes rather than helper
  methods returning widgets: classes give Flutter a stable tree
  node to reuse, methods do not.
- Reach for `ListView.builder`, image caching, and profiling
  (DevTools) before reaching for micro-optimisations.

# 04 — State Management

"State management" in Flutter means: where does changing data
live, who can change it, and how do widgets learn it changed?
Flutter has no single mandated answer — it has a ladder. Start on
the lowest rung that fits, and climb only when the current rung
hurts.

Official overview: https://docs.flutter.dev/data-and-backend/state-mgmt/options

## Rung 0: setState (built in, no package)

Data that belongs to one widget and nobody else — a counter, a
checkbox, which tab is open — is `StatefulWidget` + `setState`
(guide 03). This is not a beginner crutch to be ashamed of; it is
the correct tool for *local UI state* at every skill level.

Outgrow it when: the same data is needed by widgets in different
branches of the tree, or business logic is piling up inside
`build` and event handlers.

## The idea underneath everything: InheritedWidget

Flutter's built-in mechanism for "an ancestor holds a value and
descendants can read it and rebuild when it changes" is
`InheritedWidget`. `Theme.of(context)` and `MediaQuery.of(context)`
are exactly this. Every package below is, at heart, a friendlier
wrapper around this idea plus conventions for *changing* the value.
You rarely write a raw `InheritedWidget` in app code, but knowing
it exists demystifies all of the packages.

## Rung 1: provider — the official starting point

`provider` (**6.1.5+1**) is the package the Flutter documentation
recommends first for app-wide state. It exposes objects down the
tree and rebuilds listeners on change:

```dart
class Cart extends ChangeNotifier {
  final items = <String>[];
  void add(String item) {
    items.add(item);
    notifyListeners();
  }
}

// At the app root:
ChangeNotifierProvider(
  create: (_) => Cart(),
  child: const MyApp(),
)

// In a widget — rebuild when the cart changes:
final count = context.watch<Cart>().items.length;

// In a callback — read without subscribing:
context.read<Cart>().add('book');
```

`watch` in `build`, `read` in callbacks. That distinction is the
whole beginner learning curve of provider, and it is small. Choose
provider when you want the documented, lowest-surprise default.

## Rung 2a: Riverpod — provider's ideas, without the tree

Riverpod (**3.5.0**) declares providers as top-level objects that
do not depend on the widget tree, which makes state easier to test
and reuse, and catches several provider misuse errors at compile
time:

```dart
final counterProvider = NotifierProvider<Counter, int>(Counter.new);

class Counter extends Notifier<int> {
  @override
  int build() => 0;
  void increment() => state++;
}

// In a ConsumerWidget:
final count = ref.watch(counterProvider);
ref.read(counterProvider.notifier).increment();
```

**Riverpod 3.x migration warning:** the old workhorses
`StateProvider` and `StateNotifierProvider` moved to a legacy
import — `package:flutter_riverpod/legacy.dart`. Code samples
written for Riverpod 2 will not compile as-is against 3.x until
those imports (or a move to `NotifierProvider`) are sorted out.
Check which major a tutorial targets before copying it.

Choose Riverpod for larger apps that want compile-safe, testable
state with a strong code-generation option (`riverpod_generator`).

## Rung 2b: flutter_bloc — explicit events and states

`flutter_bloc` (**9.1.1**) implements the BLoC pattern: UI sends
*events* in, a bloc transforms them into a stream of *states* out.
More ceremony, very predictable, excellent for teams and for
flows with complex rules:

```dart
sealed class CounterEvent {}
final class Increment extends CounterEvent {}

class CounterBloc extends Bloc<CounterEvent, int> {
  CounterBloc() : super(0) {
    on<Increment>((event, emit) => emit(state + 1));
  }
}
```

Choose bloc when the app is event-driven by nature (forms with
validation rules, multi-step flows, auditability) or when a team
already standardises on it. The sealed-class state style from
guide 02 fits bloc perfectly — exhaustive switches over states in
the UI, compile errors when a case is missed.

## Signals: fine-grained reactivity

`signals_flutter` brings the signals model (popularised by web
frameworks) to Flutter: a value that automatically tracks who
read it and rebuilds only those widgets:

```dart
final count = signal(0);
// in build:
Text('${count.value}');   // this widget re-runs when count changes
count.value++;
```

Signals shine for dense, frequently-updating local state. They are
a newer addition to the ecosystem — evaluate maturity for your
project rather than assuming they replace the rungs above.

## Dependency injection: get_it

State packages decide how UI observes data. A *service locator*
like `get_it` (**9.3.0**) answers a different question: how do
classes get their dependencies (repositories, API clients) without
constructing them inline?

```dart
final getIt = GetIt.instance;
getIt.registerSingleton<ApiClient>(ApiClient());
getIt.registerFactory<CartRepository>(() => CartRepository(getIt()));

// elsewhere:
final repo = getIt<CartRepository>();
```

Register at startup in `main`, resolve where needed, and register
fakes in tests. get_it pairs with any state solution above — bloc
and Riverpod users often use it for the non-UI object graph. Keep
registrations in one obvious file; a locator nobody can audit
becomes magic.

## Decision guide

| Situation | Reach for |
|---|---|
| State inside one widget | `setState` — no package |
| First app-wide state, want the documented path | provider |
| Large app, compile-safe + testable state, codegen welcome | Riverpod 3 |
| Event-driven flows, team standard, strict predictability | flutter_bloc |
| Dense reactive local state, experimenting | signals_flutter |
| Constructing repositories/services cleanly (with any above) | get_it |

Rules that hold regardless of choice:

- **One solution per app** for UI state (DI locator aside). Mixing
  provider, Riverpod, and bloc in one codebase is how state bugs
  become archaeology.
- Keep business logic out of widgets: widgets render state and
  forward gestures; notifiers/blocs/repositories do the work.
- State types as sealed classes + exhaustive switches (guide 02)
  make "impossible" UI states unrepresentable.
- Whatever you pick, write down *why* in the project readme —
  future you will otherwise re-litigate it.

Versions drift: verify the current version on
https://pub.dev before adding any of these to `pubspec.yaml`.

# 05 — Navigation and Routing

Navigation is moving between screens and — on mobile and the web —
honouring the URLs and deep links that arrive from outside the app.
Flutter gives you a raw navigator and one dominant routing package.
Learn the raw tool, then use the package.

Official docs: https://docs.flutter.dev/ui/navigation

## Navigator: the built-in stack

Screens live on a stack. Push adds one, pop removes one:

```dart
Navigator.of(context).push(
  MaterialPageRoute<void>(builder: (_) => const DetailsPage()),
);
Navigator.of(context).pop();   // back
```

Returning a result from a pushed screen:

```dart
final picked = await Navigator.of(context).push<String>(
  MaterialPageRoute(builder: (_) => const PickerPage()),
);
// in PickerPage: Navigator.of(context).pop('chosen value');
```

Named routes (`routes:` map + `pushNamed`) exist on `MaterialApp`,
but stringly-typed names with untyped arguments are exactly where
bugs breed. For anything past a demo, use the declarative router
below, which is also how deep links become tractable.

## go_router: the standard choice

`go_router` (**18.1.4**) is maintained in the official
`flutter/packages` repository and is the routing package the
Flutter team points developers to. Routes are declared as a tree
of paths; navigation is by location string or by route name:

```dart
final router = GoRouter(
  routes: [
    GoRoute(
      path: '/',
      builder: (_, _) => const HomePage(),
      routes: [
        GoRoute(
          path: 'items/:id',
          name: 'item',
          builder: (_, state) =>
              ItemPage(id: state.pathParameters['id']!),
        ),
      ],
    ),
  ],
);

MaterialApp.router(routerConfig: router);
```

Navigate imperatively when needed:

```dart
context.go('/items/42');        // replace the stack with this location
context.push('/items/42');      // stack it on top (back returns here)
context.goNamed('item', pathParameters: {'id': '42'});
```

`go` vs `push` is the one distinction to internalise: `go` declares
"the app *is at* this location" (tabs, top-level sections), `push`
is a detour the user backs out of (details, editors).

## Type-safe routes with go_router_builder

Path strings and `pathParameters['id']!` work, but they are
unchecked. `go_router_builder` generates typed route classes from
annotations, so wrong parameters stop compiling:

```dart
@TypedGoRoute<ItemRoute>(path: '/items/:id')
class ItemRoute extends GoRouteData with $ItemRoute {
  const ItemRoute({required this.id});
  final int id;

  @override
  Widget build(BuildContext context, GoRouterState state) =>
      ItemPage(id: id);
}

// call site — fully typed:
const ItemRoute(id: 42).go(context);
```

The generation step runs through `build_runner` — the same
workflow as JSON models in guide 06:

```powershell
dart run build_runner watch --delete-conflicting-outputs
```

Adopt the builder when routes gain query parameters, multiple
parameterised branches, or a team tired of string typos.

## Shell routes: persistent chrome

Tabs or a sidebar that stay on screen while inner content changes
are a *shell*: `StatefulShellRoute.indexedStack` keeps one
navigation stack per branch, so each tab remembers its place.
Reach for it instead of hand-rolling a `BottomNavigationBar` that
swaps bodies and throws away scroll positions and back stacks.

## Deep links

A deep link is an ordinary URL — `https://example.com/items/42`,
or an app scheme link — that should open the matching screen, from
a browser, an email, a notification, or another app.

With go_router, deep links are mostly already done: because the
app's location *is* a URL-shaped path, a link to `/items/42`
resolves through the same route table. Your remaining work is
platform registration:

- **Android:** an intent filter for your scheme/host in
  `AndroidManifest.xml`, plus App Links verification
  (`assetlinks.json` hosted on your domain) so links open the app
  instead of the browser.
- **iOS:** Associated Domains entitlement + `apple-app-site-association`
  hosted on your domain.
- **Web:** nothing extra — the URL is native there.

Test links cold (app killed) and warm (app running): the two paths
differ, and only cold testing catches missing registrations.

Platform setup changes over time — follow the current steps at
https://docs.flutter.dev/ui/navigation/deep-linking rather than
copying manifest snippets from old posts.

## Guards: redirects

Authentication gates and onboarding checks belong in one place:
go_router's `redirect`. It runs on every navigation and can send
the user elsewhere:

```dart
GoRouter(
  refreshListenable: authState,   // re-run redirect when auth changes
  redirect: (context, state) {
    final loggedIn = authState.isLoggedIn;
    final loggingIn = state.matchedLocation == '/login';
    if (!loggedIn && !loggingIn) return '/login';
    if (loggedIn && loggingIn) return '/';
    return null;   // no redirect
  },
  routes: [ /* ... */ ],
);
```

Keep redirect logic small and total: it runs constantly, and a
redirect loop (A sends to B, B sends to A) hangs the app on a
blank screen. Always allow the destination itself through.

## Passing data between screens

Preference order, safest first:

1. **In the URL** — ids and filters (`/items/42?tab=reviews`).
   Survives deep links, restarts, and sharing.
2. **Typed route parameters** via go_router_builder (above).
3. **`extra`** — an in-memory object passed with `push`. Fine for
   a quick hand-off; it does *not* survive a deep link or a state
   restoration, so never make it the only copy of anything.

If a screen cannot rebuild itself from its URL plus your data
layer, it will break on deep links — that test is the design rule.

## Common mistakes

- Reading route arguments from a context *above* the router.
- Using `Navigator` and go_router interchangeably in one feature —
  pick the router's API inside routed code.
- Putting a whole object in the URL instead of its id.
- Forgetting `refreshListenable`, so login/logout does not
  re-trigger redirects until the next manual navigation.
- Hard-coding the initial route instead of letting a deep link in.

Verify the current go_router version on https://pub.dev before
adding it — 18.x is the line this guide was written against.

# 06 — Networking and Data

Most apps talk to a JSON API. The Dart pattern is stable: an HTTP
client fetches text, generated model classes turn JSON into typed
objects, a repository hides both from the UI, and errors are
values the UI can render — not exceptions that escape.

HTTP docs: https://docs.flutter.dev/data-and-backend/networking

## Choosing an HTTP client

### http — the simple default

`http` (**1.6.0**) is the lightweight client the Flutter docs use.
For straightforward GET/POST JSON work it is all most apps need:

```dart
import 'package:http/http.dart' as http;

Future<List<dynamic>> fetchItems() async {
  final response = await http.get(
    Uri.parse('https://api.example.com/items'),
    headers: {'Accept': 'application/json'},
  );
  if (response.statusCode != 200) {
    throw HttpException('Failed: ${response.statusCode}');
  }
  return jsonDecode(response.body) as List<dynamic>;
}
```

Always build URIs with `Uri.parse` / `Uri.https` — never string-
concatenate query parameters (escaping bugs and injection bugs).

### dio — the power tool

`dio` (**5.11.1**) earns its place when you need what `http` does
not bundle: interceptors (auth token attach + refresh in one
place), request cancellation, timeouts per request, upload/download
progress, and form data without hand-rolling:

```dart
final dio = Dio(BaseOptions(baseUrl: 'https://api.example.com'));
dio.interceptors.add(InterceptorsWrapper(
  onRequest: (options, handler) {
    options.headers['Authorization'] = 'Bearer $token';
    handler.next(options);
  },
));
```

Rule of thumb: start with `http`; move to `dio` when a second
feature needs an interceptor or cancellation — not on day one
"out of habit".

## Models: never hand-write fromJson at scale

Manual `fromJson` factories work for one model and rot by the
tenth. The standard is code generation with `build_runner`
(**2.17.1**) driving a generator. Remember from guide 02: Dart
macros were abandoned — `build_runner` *is* the codegen route.

### json_serializable — the plain option

`json_serializable` (**6.15.2**) generates `fromJson`/`toJson` for
an annotated class:

```dart
import 'package:json_annotation/json_annotation.dart';
part 'item.g.dart';

@JsonSerializable()
class Item {
  const Item({required this.id, required this.name, this.priceCents});
  factory Item.fromJson(Map<String, dynamic> json) => _$ItemFromJson(json);

  final int id;
  final String name;
  final int? priceCents;

  Map<String, dynamic> toJson() => _$ItemToJson(this);
}
```

### freezed — the full-featured option

`freezed` (**4.0.3**) generates the model *plus* equality,
`copyWith`, and union (sealed) types — the same sealed-state style
as guides 02 and 04:

```dart
@freezed
sealed class Item with _$Item {
  const factory Item({required int id, required String name}) = _Item;
  factory Item.fromJson(Map<String, dynamic> json) => _$ItemFromJson(json);
}
```

**Version quirk, read carefully:** with freezed 4.x you pin the
*annotation* package at **3.1.0** (`freezed_annotation: 3.1.0`)
while the generator package is 4.0.3. The mismatched majors are
intentional in this release line — "fixing" them to match breaks
the build. Check the freezed readme for the current pairing
before changing either number.

### The build_runner workflow

Generated files (`*.g.dart`, `*.freezed.dart`) live next to your
sources and are checked in like normal code:

```powershell
# one-off generation after editing a model:
dart run build_runner build --delete-conflicting-outputs

# regenerate continuously while you work:
dart run build_runner watch --delete-conflicting-outputs
```

Typical `pubspec.yaml` shape (verify versions on pub.dev):

```yaml
dependencies:
  http: ^1.6.0            # or dio: ^5.11.1
  json_annotation: ^4.9.0
  freezed_annotation: 3.1.0   # pinned — see the quirk above

dev_dependencies:
  build_runner: ^2.17.1
  json_serializable: ^6.15.2
  freezed: ^4.0.3
```

If generation fails, read the *first* error — build_runner output
is long, and later errors are usually echoes of the first.

## Structure: a repository between API and UI

Widgets should never import `http` or `dio` directly:

```dart
class ItemRepository {
  ItemRepository(this._client);
  final http.Client _client;
  List<Item>? _cache;

  Future<List<Item>> getItems() async {
    if (_cache != null) return _cache!;
    final response = await _client.get(
      Uri.https('api.example.com', '/items'),
    );
    if (response.statusCode != 200) {
      throw ItemLoadException(response.statusCode);
    }
    final list = jsonDecode(response.body) as List<dynamic>;
    return _cache = [
      for (final j in list) Item.fromJson(j as Map<String, dynamic>),
    ];
  }
}
```

Benefits you feel immediately: one place for the base URL, one
place for caching, and tests can pass a fake client (guide 08).

## Error handling

- **Model errors as states, not snackbars from the data layer.**
  The repository throws typed exceptions or returns a sealed
  result; the state layer converts that into a `Failed` state
  (guide 04); the UI renders it with a retry button.
- **Distinguish failure kinds:** no connectivity, timeout,
  401 (re-auth), 404 (gone), 5xx (retry later), and malformed
  JSON (your bug or the API's breaking change) need different
  messages and different retry behaviour.
- **Set timeouts.** Both clients support them; an unbounded wait
  is a hung app.
- **Never log tokens or full auth headers**, even in debug builds
  that might get shared.

## Caching, honestly

Three levels, in order of sanity:

1. **In-memory** (the repository field above) — free, gone on
   restart, right for most screens.
2. **HTTP caching semantics** — honour `ETag`/`Cache-Control` if
   your API sends them; dio interceptors make this practical.
3. **On-disk** — persist responses in local storage (guide 07)
   only when offline use is a real requirement; now you own
   invalidation, and invalidation is the hard part.

For big JSON responses, parse off the main isolate
(`Isolate.run`, guide 02) so scrolling never stutters.

# 07 — Local Storage

Local storage is three different jobs that get confused constantly:
remembering a few settings, storing structured app data, and
keeping files. Each job has a right tool — and the NoSQL job has a
trap this guide flags in capital letters.

Storage docs: https://docs.flutter.dev/data-and-backend

## Job 1: a few small settings — shared_preferences

`shared_preferences` (**2.5.6**) wraps the platform key-value
stores (Android SharedPreferences, iOS UserDefaults). It is for
*small, simple* values only: flags, a theme choice, the last tab.

```dart
final prefs = await SharedPreferences.getInstance();
await prefs.setBool('seen_onboarding', true);
await prefs.setString('theme', 'dark');

final seen = prefs.getBool('seen_onboarding') ?? false;
```

Hard limits to respect:

- Strings, bools, ints, doubles, and string lists — nothing else.
- **Not** a database: no queries, no transactions, no large blobs.
  Storing your app's data here as JSON strings is the classic
  mistake this section exists to prevent.
- **Not secure:** values are readable on a rooted/jailbroken
  device. Never store tokens or secrets here (see the end).

## Job 2: structured data — a real database

### drift — the default recommendation

`drift` (**2.35.4**) is a reactive persistence library on top of
SQLite, and it is the default choice for new Flutter apps that
store structured local data. You declare tables in Dart, drift
generates type-safe queries, and queries can be *watched* as
streams so the UI updates when the data changes:

```dart
class Items extends Table {
  IntColumn get id => integer().autoIncrement()();
  TextColumn get name => text()();
  IntColumn get priceCents => integer().nullable()();
}

@DriftDatabase(tables: [Items])
class AppDatabase extends _$AppDatabase {
  AppDatabase(super.e);

  @override
  int get schemaVersion => 1;

  Stream<List<Item>> watchItems() => select(items).watch();
  Future<int> addItem(ItemsCompanion entry) => into(items).insert(entry);
}
```

Generation runs through `build_runner`, same as guide 06. Drift
brings compile-time-checked SQL, migrations with tests, and web/
desktop support. If you are choosing one database today, choose
this one.

### sqflite — the older direct-SQL route

`sqflite` (**2.4.6**) gives you raw SQLite with hand-written SQL
strings. It is mature and fine in existing apps. In new apps it
mostly survives where a team wants zero code generation and is
disciplined about SQL — accepting that a typo'd column name is a
runtime error instead of a compile error, which is precisely the
trade drift exists to remove.

## Files: path_provider + dart:io

Documents, downloads, cached images, exports — anything that is a
file belongs in a platform directory you ask for, never a
hard-coded path:

```dart
import 'package:path_provider/path_provider.dart';

final docs = await getApplicationDocumentsDirectory();  // survives, backed up
final cache = await getTemporaryDirectory();            // system may clear it

final file = File('${docs.path}/export.csv');
await file.writeAsString(csvText);
```

Rule: documents directory for data the user would miss, temporary
directory for anything you can recreate. On desktop, the same API
returns the platform-appropriate folders.

## WARNING: Hive and Isar — the originals are stale

This is the most expensive trap in Flutter storage, because old
tutorials still recommend both packages as defaults:

- **`hive` 2.2.3 has not been meaningfully updated since 2022.**
- **`isar` 3.1.0+1 has not been meaningfully updated since 2023.**

Do **not** start a new project on the original `hive` or `isar`
packages. If you want that style of embedded NoSQL store, use the
maintained community forks instead:

- **`hive_ce`** — the community edition continuing Hive.
- **`isar_community`** — the community fork continuing Isar.

…or use **ObjectBox**, a separately maintained embedded database
with a Flutter package, if its model fits your data.

Whichever you pick, say so in the project readme with the reason —
the next developer will otherwise "helpfully" migrate you back to
the stale originals that search results still rank first.

Honest framing: for most apps this whole NoSQL category is
optional. drift over SQLite covers the structured-data job with
the strongest tooling, and choosing it means one less dependency
betting on fork maintenance.

## Secrets: neither of the above

Tokens, refresh credentials, and API keys are not "settings" and
not "data". Store them in the platform keystore/keychain through
a secure-storage package (search pub.dev for the current
maintained option and verify it before adopting), keep them out
of `shared_preferences` and out of the database, and keep them out
of source control entirely. A secret that ships inside the app
binary is a published secret — design APIs accordingly.

## Choosing, in one table

| Job | Tool |
|---|---|
| A handful of flags/settings | shared_preferences 2.5.6 |
| Structured app data, queries, reactive UI | **drift 2.35.4** (default) |
| Existing raw-SQL codebase | sqflite 2.4.6 |
| Files, exports, caches | path_provider + `dart:io` |
| Embedded NoSQL, if you truly need it | hive_ce / isar_community forks, or ObjectBox — **never stale hive/isar originals** |
| Tokens and secrets | Platform keystore via a secure-storage package |

## Migrations are part of the choice

Any database you ship will change schema after users have data.
Before release 1.0, confirm your choice has a migration story you
understand (drift: versioned schema + migration tests; sqflite:
`onUpgrade` by hand) and write the first migration test while the
schema is still trivial — retrofitting migration discipline after
version 3 is where local-data horror stories come from.

Verify current versions on https://pub.dev before adding any of
these — storage packages in particular have look-alike forks.

# 08 — Testing

Flutter's test story is one of its strengths: the same Dart code
runs unit tests, widget tests in a simulated environment, golden
(screenshot) tests, and full integration tests on a real device —
all driven by `flutter test`. The discipline is layering: many
fast tests at the bottom, few slow ones at the top.

Testing docs: https://docs.flutter.dev/testing/overview

## The layers

| Layer | What it proves | Speed | Where it lives |
|---|---|---|---|
| Unit | One class/function behaves | Milliseconds | `test/` |
| Widget | One widget renders + reacts | Fast, no device | `test/` |
| Golden | Pixels did not change unexpectedly | Fast | `test/` |
| Integration | The whole app works on a device | Slow, real device/emulator | `integration_test/` |

If a behaviour can be tested at a lower layer, test it there.
Integration tests are for wiring and platform behaviour, not for
re-proving your business logic one slow boot at a time.

## Unit tests

Plain Dart, no Flutter runtime needed. This is where repositories,
models, and state logic (guides 04 and 06) earn their keep —
design them to be constructible with fakes and they are trivial
to test:

```dart
import 'package:flutter_test/flutter_test.dart';

void main() {
  test('cart totals add up', () {
    final cart = Cart();
    cart.add('book', priceCents: 1200);
    cart.add('pen', priceCents: 300);
    expect(cart.totalCents, 1500);
  });

  test('empty cart totals zero', () {
    expect(Cart().totalCents, 0);
  });
}
```

Group related cases with `group(...)`, and name tests as
sentences about behaviour, not about methods.

## Mocking with mocktail

When a class depends on an API client or a database, substitute a
fake. `mocktail` is the common Dart choice because it needs no
code generation and is null-safety native:

```dart
class MockApiClient extends Mock implements ApiClient {}

void main() {
  test('repository maps a 200 into items', () async {
    final api = MockApiClient();
    when(() => api.getItems()).thenAnswer((_) async => ['a', 'b']);

    final repo = ItemRepository(api);
    expect(await repo.getItems(), ['a', 'b']);
    verify(() => api.getItems()).called(1);
  });
}
```

Prefer hand-written fakes for simple interfaces (a class with
canned answers is easier to read than a wall of `when(...)`), and
mocktail when the interface is wide or you need verification.
Verify the current mocktail version on pub.dev before adding it.

## Widget tests

Widget tests pump a widget into a test environment and interact
with it through finders and gestures — no emulator required:

```dart
testWidgets('counter increments on tap', (tester) async {
  await tester.pumpWidget(const MaterialApp(home: CounterPage()));

  expect(find.text('0'), findsOneWidget);

  await tester.tap(find.byIcon(Icons.add));
  await tester.pump();   // run one frame after the tap

  expect(find.text('1'), findsOneWidget);
});
```

Essential vocabulary:

- `tester.pumpWidget(...)` — build the widget tree.
- `find.text`, `find.byType`, `find.byKey`, `find.byIcon` — locate.
- `tester.tap`, `tester.enterText`, `tester.drag` — interact.
- `tester.pump()` — advance one frame; `pumpAndSettle()` — run
  until animations finish (careful: it times out on infinite
  animations like a spinning progress indicator).
- Wrap the widget under test in `MaterialApp` (or the app's real
  theme/providers) — most widgets assume those ancestors exist.

Widget tests are the workhorse for screens: states render, buttons
call callbacks, error states appear when the state says so.

## Golden tests: pixels as the assertion

A golden test renders a widget and compares it, pixel by pixel,
against a committed reference image:

```dart
testWidgets('item card golden', (tester) async {
  await tester.pumpWidget(
    const MaterialApp(home: ItemCard(name: 'Book', priceCents: 1200)),
  );
  await expectLater(
    find.byType(ItemCard),
    matchesGoldenFile('goldens/item_card.png'),
  );
});
```

Workflow:

```powershell
flutter test --update-goldens   # create / refresh reference images
flutter test                     # compare against them
```

Rules for goldens that do not become a burden:

- Golden-test *components and key screens*, not every widget.
- A golden failure means "pixels changed" — sometimes that is the
  change you intended (update the goldens and review the diff in
  the pull request), sometimes it is a regression. The review of
  the image diff is the test.
- Fonts and platform rendering differ between machines. Generate
  and compare goldens on the same platform — in practice, let CI
  own the golden images, and load real fonts in the test setup if
  text rendering matters.

## Integration tests

Integration tests run the real app on a device or emulator and
drive it end to end — the smoke test that the pieces are wired
together. They live in `integration_test/` and use the
`integration_test` package.

**Non-negotiable setup detail:** `integration_test` comes from
the Flutter SDK, never from pub. In `pubspec.yaml` it is declared
exactly like this:

```yaml
dev_dependencies:
  integration_test:
    sdk: flutter
```

If you ever see a version number pinned against `integration_test`
from pub.dev in a project, that is a version mix-up — fix it to
the SDK form above.

```dart
// integration_test/app_test.dart
import 'package:integration_test/integration_test.dart';

void main() {
  IntegrationTestWidgetsFlutterBinding.ensureInitialized();

  testWidgets('sign in and see the home screen', (tester) async {
    app.main();
    await tester.pumpAndSettle();

    await tester.enterText(find.byKey(const Key('email')), 'a@b.c');
    await tester.enterText(find.byKey(const Key('password')), 'secret');
    await tester.tap(find.byKey(const Key('sign_in')));
    await tester.pumpAndSettle();

    expect(find.text('Welcome'), findsOneWidget);
  });
}
```

```powershell
flutter test integration_test/app_test.dart -d <device-id>
```

Keep integration tests few, stable, and about the critical path
(sign in, core flow, purchase-shaped flow). Flaky integration
tests get deleted; design them against keys and real waiting
conditions, not fixed sleeps, so they survive.

## Running everything, and CI

```powershell
dart format --set-exit-if-changed .
flutter analyze
flutter test
```

That trio is the local gate and the CI gate — same commands, so
"green on my machine" and "green in CI" mean the same thing. In
CI, run unit/widget/golden tests on every pull request (fast, no
device farm needed), and integration tests on an emulator or
device job on merge or nightly, where their cost is justified.

Before declaring any change done, be able to say which of these
actually ran — format, analyze, tests, and a build for the target
platform — and label anything that did not run as Unverified
rather than assuming it would pass.

# 09 — Windows Desktop

Flutter's Windows desktop support is stable, and a Windows app is a
normal Flutter app whose runner happens to be a small native Win32/C++
program. You can only build the Windows app **on Windows** — desktop
apps always build on their own operating system (see
[guide 11](11-web-and-other-platforms.md)).

Snapshot this guide was written against: **Flutter 3.50.0 / Dart
3.14.0**. Windows **flavors** (separate build variants) need **Flutter
3.47 or newer** — see [guide 12](12-flavors-and-config.md).

## What you need installed

1. **Flutter SDK** (see [guide 01](01-getting-started-and-toolchain.md)).
2. **Visual Studio 2022** (not VS Code) with the **"Desktop development
   with C++" workload**. This is the part people miss: Flutter builds
   the Windows runner with Visual Studio's C++ toolchain and CMake.
   In the Visual Studio Installer, tick that workload; it brings the
   MSVC compiler, the Windows SDK, and CMake.
3. Run `flutter doctor` and fix everything it flags for Windows before
   you start. A clean `flutter doctor -v` for the Windows toolchain is
   the real "ready" signal.

## Creating and running a Windows app

```powershell
# New project with Windows enabled from the start
flutter create --platforms=windows,android my_app

# Add Windows to an existing project (run inside the project)
flutter create --platforms=windows .

# Run it on Windows
flutter run -d windows

# Build the release version
flutter build windows --release
```

## Where the build output lands

```
build\windows\x64\runner\Release\
```

That whole **Release folder is the app**. It contains:

| Item | What it is |
|---|---|
| `my_app.exe` | The runner executable (your app name) |
| `flutter_windows.dll` | The Flutter engine for Windows |
| `data\` | Your compiled Dart code (`app.so`), assets, fonts, and the ICU data file |
| Plugin DLLs | One `.dll` per native plugin your app uses |

**Ship the whole folder, never just the `.exe`.** The executable alone
does nothing — it needs the engine DLL and the `data\` folder next to
it. Copying only the exe is the most common Windows distribution
mistake.

## The runner folder, briefly

```
windows\
  CMakeLists.txt        Build definition for the native side
  runner\
    main.cpp            Entry point — creates the window, starts Flutter
    flutter_window.cpp  Hosts the Flutter view inside the Win32 window
    win32_window.cpp    Plain Win32 window plumbing
    Runner.rc / resources\app_icon.ico   App icon
  flutter\              Generated — do not edit by hand
```

You rarely touch `main.cpp`. The files you *will* touch: the icon
(`app_icon.ico`), and `Runner.rc` if you need to change version info or
the product name shown in Windows.

## Window size, title, and behaviour

Out of the box the window size and title come from the runner code.
For real control — minimum size, starting size, centering, title,
always-on-top, frameless, show/hide — the community standard is the
**`window_manager` package (0.7.0)**. Be clear about what it is:

- `window_manager` is a **community package** by leanflutter, **not a
  Flutter-team package**. It is widely used and actively maintained
  (0.7.0, published 2026-11-12), but it is a third-party dependency —
  check its pub.dev page before pinning it, per this pack's rules.
- It must be initialised before `runApp`, and the window shown
  explicitly, or the app can flash or start hidden.

```dart
import 'package:window_manager/window_manager.dart';

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await windowManager.ensureInitialized();

  const options = WindowOptions(
    size: Size(1100, 720),
    minimumSize: Size(720, 480),
    center: true,
    title: 'My App',
  );
  await windowManager.waitUntilReadyToShow(options, () async {
    await windowManager.show();
    await windowManager.focus();
  });

  runApp(const MyApp());
}
```

Keep window setup in one place (your composition root, see
[guide 14](14-architecture-and-project-structure.md)) so tests and
other platforms never depend on it — `window_manager` calls belong
behind a platform check (`Platform.isWindows` etc.), because the same
`main.dart` serves Android and web where they do not apply.

## System tray

There is no tray support in the Flutter SDK itself. The community
package is **`tray_manager` (0.9.0)** — also by leanflutter, also
**not a Flutter-team package** (published 2026-11-12; re-check on
pub.dev). It provides the tray icon, context menu, and click events.
Typical pattern:

- Add a tray icon with a context menu (Open / Quit).
- Decide what closing the window means: for a tray app, intercept the
  close (via `window_manager`'s listener) and **hide** instead of
  exiting; Quit in the tray menu does the real exit.
- Ship a proper `.ico` for the tray — a blurry tray icon is the first
  thing users see.

## Single instance

Flutter does not enforce a single instance for you. If a second launch
should focus the existing window instead of opening a duplicate,
handle it in the native runner or with a community single-instance
package — and decide this early, because retrofitting it after users
have two copies running is fiddly. For most tray/utility apps, single
instance is the right default.

## Distribution: folder or MSIX

Two honest options:

1. **Ship the Release folder.** Zip the whole
   `build\windows\x64\runner\Release\` folder, or feed that folder to
   any folder-based installer/packager you use (the pattern: installer
   takes a folder of files in, produces a setup program and a portable
   zip out). This is simple, transparent, and works everywhere. Users
   extract/install and run the exe; no store involved.
2. **MSIX for the Microsoft Store (or managed installs).** The
   community **`msix` package** turns the Release output into an
   `.msix`: add it as a dev dependency, put the `msix_config:` block
   in `pubspec.yaml` (identity, publisher, display name, logo), then:

   ```powershell
   dart run msix:create
   ```

   MSIX for the Store must be signed with your Store identity; a
   self-signed MSIX only installs where its certificate is trusted.
   Pick MSIX when you need the Store or clean per-user
   install/uninstall semantics — not by default.

Whichever route: bump `version:` in `pubspec.yaml` before building
(see [guide 10](10-android-release.md) — the same version string drives
every platform), test the packaged build on a machine (or VM) without
Flutter installed, and confirm the app starts from a cold folder copy.

## Windows-specific traps

- **Build only on Windows.** CI for Windows builds needs a Windows
  runner; the same repo can build Android on Linux and Windows on
  Windows in parallel jobs.
- **Debug builds are not shippable.** Always distribute `--release`
  (see build modes in [guide 13](13-performance-and-devtools.md)).
- **Antivirus false positives** happen occasionally with fresh unsigned
  executables; code signing is what fixes reputation over time, and
  the Store/MSIX route sidesteps some of it.
- **Long paths / spaces:** keep the project path short and plain
  (e.g. `C:\dev\my_app`) — native toolchains still trip over very long
  or exotic paths.

## Checklist

- [ ] Visual Studio C++ workload installed; `flutter doctor` clean
- [ ] `flutter build windows --release` succeeds
- [ ] The whole Release folder copied somewhere clean runs standalone
- [ ] Window size/minimum/title set deliberately (window_manager or runner)
- [ ] Tray behaviour (if any) decided: hide-on-close vs exit
- [ ] Single-instance behaviour decided
- [ ] Distribution route chosen: folder/installer or MSIX

# 10 — Android Release

Shipping a Flutter app to Google Play is mostly the standard Android
release story with a Flutter front door: you build an **Android App
Bundle (.aab)**, signed through **Play App Signing**, from a release
build with code shrinking on. This guide covers the parts that are
specific enough to get wrong.

Snapshot: **Flutter 3.50.0 / Dart 3.14.0**, Play target-API era
**API 36** (see the deadlines reference in the Kotlin/Android material
and re-check Play Console help — the target requirement rises most
years).

## The version lives in pubspec.yaml

```yaml
version: 1.0.0+1
```

- `1.0.0` is the **versionName** users see.
- `+1` is the **versionCode** — the integer Play uses to order
  releases. Every upload to Play needs a **higher** versionCode than
  the last one, or Play rejects it.
- Flutter feeds both into the Android build automatically. Do not also
  hard-code them in Gradle; one source of truth.

Bump the version **before** the release build, every time.

## Signing: upload key + Play App Signing

Play App Signing is the model, and it is not optional for new apps:

- **Google holds the final app signing key** (the one devices trust).
- **You hold an upload key** — it only proves the upload came from
  you. If you lose it, Google can reset it after identity checks; if
  you lose the *app* signing key in the old pre-Play-Signing world
  there was no recovery, which is exactly why this model exists.

Create the upload keystore once (JDK `keytool`):

```powershell
keytool -genkeypair -v -keystore upload-keystore.jks `
  -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

Wire it up **outside version control**:

1. `android/key.properties` (git-ignored) points at the keystore and
   alias, with passwords read from there or the environment:

   ```properties
   storePassword=…
   keyPassword=…
   keyAlias=upload
   storeFile=C:/path/to/upload-keystore.jks
   ```

2. `android/app/build.gradle.kts` loads `key.properties` if present
   and uses it for the `release` signing config; if the file is
   absent, release signing is left unset (so CI and other machines
   fail loudly instead of silently shipping a debug-signed bundle).
3. **Never commit** the keystore or real passwords. Back the keystore
   up somewhere safe and separate — losing it means an upload-key
   reset process, not instant death, but it is still a bad week.

Flutter's own docs walk this file-by-file ("Build and release an
Android app" on docs.flutter.dev) — follow them for the exact Gradle
snippets for your Flutter version, and keep the structure above.

## Build the bundle

```powershell
flutter build appbundle --release
```

Output:

```
build/app/outputs/bundle/release/app.aab
```

That `.aab` is what you upload to Play Console. (An APK —
`flutter build apk --release` — is for direct distribution and
testing, not for Play uploads.)

## Code shrinking (R8) is on by default

Release builds run **R8** code shrinking and resource shrinking by
default in current Flutter/Android tooling. Practical consequences:

- Smaller bundle, dead code removed — good.
- Reflection-heavy plugins occasionally need **keep rules** in
  `android/app/proguard-rules.pro`. A release-only crash that debug
  never shows is the classic symptom: test the **release** build on a
  real device before uploading, not just debug.
- Keep the mapping files from each release build (Play accepts them
  for deobfuscated crash reports; they live under
  `build/app/outputs/mapping/release/`).

## Target API and Play requirements

- The Flutter/Android toolchain sets `targetSdk` from the Flutter
  version's defaults; current-era Flutter targets **API 36**, which
  matches Play's requirement for new apps and updates in this era.
- After upgrading Flutter, confirm the effective target in the built
  bundle rather than assuming — Play rejects uploads below the
  required target, and the requirement steps up on a published
  schedule (extensions exist but are a delay, not a strategy).
- Play also requires the App Bundle format and Play App Signing —
  both already covered above — plus the usual Console declarations
  (data safety, content rating, target audience). Those live in Play
  Console, not in the codebase; do them deliberately, they are part
  of the release.

## Flavors on Android

Android flavors are **Gradle product flavors** on the Android side,
selected from Flutter with `--flavor`:

```powershell
flutter build appbundle --release --flavor prod -t lib/main_prod.dart
```

Each flavor can carry its own `applicationId` suffix, name, and icon,
so `dev` / `staging` / `prod` installs can sit side by side on one
phone. The full cross-platform flavor story — including `--dart-define`
config and the Windows flavor support added in Flutter 3.47 — is
[guide 12](12-flavors-and-config.md). Rule of thumb: flavors are an
Android/desktop concept implemented per platform; there is no single
switch that creates them everywhere.

## Play release tracks

Upload in steps, not straight to everyone:

1. **Internal testing** — your own small list, minutes to go live.
   First stop for every build.
2. **Closed testing** — a wider trusted group; also where new
   personal developer accounts satisfy Play's pre-production testing
   requirement.
3. **Open testing** — public opt-in beta.
4. **Production, staged rollout** — release to a percentage (e.g.
   20%), watch crashes/ratings, then halt or complete the rollout.

A build that survives internal testing with the release signing,
release shrinking, and a cold install is the build you promote — you
promote the **same bundle** up the tracks rather than rebuilding, so
what you tested is what ships.

## Pre-upload checklist

- [ ] `version:` bumped in pubspec.yaml (versionCode increased)
- [ ] `flutter analyze` clean; tests pass (guide 08)
- [ ] Release build installed and exercised on a real device
- [ ] Upload key signing in place; `key.properties` not committed
- [ ] `flutter build appbundle --release` output is the file uploaded
- [ ] Effective target API meets Play's current requirement
- [ ] Mapping files from this build saved
- [ ] Upload goes to internal testing first, then promotes

# 11 — Web and Other Platforms

Flutter targets six platforms from one codebase, but they are not all
equal and they do not all build from the same machine. This guide
covers web properly, then the honest state of iOS, macOS, and Linux.

**The one rule that governs everything below: a desktop or mobile app
builds only on its own operating system.** Windows apps build on
Windows, macOS and iOS apps build on macOS, Linux apps build on Linux.
Android and web are the exceptions — they build from any host.

Snapshot: **Flutter 3.50.0 / Dart 3.14.0**; Windows, macOS, and Linux
desktop are all **stable**.

## Flutter web

### The two renderers/build outputs

Current Flutter web builds compile your Dart to either:

- **WebAssembly (Wasm)** — the preferred modern target: better
  performance, smaller/faster code via Dart's Wasm compiler plus
  Skwasm rendering. Some packages and browser APIs are not yet
  Wasm-compatible, which is the usual reason a project cannot use it.
- **JavaScript** — the long-standing target: Dart compiled to JS with
  the CanvasKit (or HTML-era) rendering approach. Maximum
  compatibility, the fallback when Wasm blocks you.

```powershell
flutter build web --wasm        # Wasm build (preferred when it works)
flutter build web               # JavaScript build
flutter run -d chrome           # develop against Chrome
```

Output lands in `build/web/` — a static site folder you can host
anywhere (any static host, an S3 bucket, your own server). Try the
Wasm build first; if a dependency blocks it, the JS build is a
perfectly respectable ship, not a failure.

### Web realities to design for

- **It is an app, not a document.** Flutter web renders to canvas;
  text selection, find-in-page, screen-reader semantics, and SEO
  behave like an app platform, not like HTML pages. For content-first
  sites, Flutter web is usually the wrong tool; for app-like tools,
  dashboards, and companions to your mobile app, it is a good one.
- **URLs and navigation** need deliberate setup — use a routing
  package (see [guide 05](05-navigation-and-routing.md)) with URL
  strategies configured, or the back button will embarrass you.
- **Startup weight matters.** First load downloads the engine; keep
  the initial screen light, defer heavy assets, and measure on a
  throttled connection, not on localhost.
- **Browser testing is part of the platform:** Chrome is the dev
  default, but check Firefox and Safari before calling it done —
  Wasm support and performance differ per browser.

## iOS

- **Builds only on macOS**, with Xcode. There is no way around this;
  teams without a Mac use a Mac CI runner.
- Signing, provisioning, and App Store submission follow Apple's
  normal rules — Flutter does not abstract them away. Budget real
  time for the first submission (certificates, App Store Connect,
  review).
- `flutter build ipa` produces the archive for distribution once
  signing is configured in Xcode.

## macOS

- **Stable**, builds only on macOS. The runner is a native macOS app;
  distribution is a `.app` bundle — ship it inside a DMG or via the
  Mac App Store.
- Store distribution requires sandboxing and entitlements; a
  sandboxed build can break file-access features that worked in a
  loose build, so test the exact distribution build.
- Window/tray behaviour uses the same community packages as Windows
  (see [guide 09](09-windows-desktop.md)) — still community, not
  Flutter-team.

## Linux

- **Stable**, builds only on Linux. Needs the GTK/CMake/Ninja
  toolchain (`flutter doctor` lists the packages for your distro).
- Output is a bundle folder (binary + `lib/` + `data/`), shipped as a
  tarball, a distro package, or a Snap/Flatpak if you want store-style
  distribution. Like Windows, **ship the whole bundle folder**, not
  just the binary.
- The audience is smaller but the platform is well behaved — if your
  users are on Linux, the incremental cost over the other desktops is
  mostly testing.

## ChromeOS

ChromeOS can be both a **host** (Linux container running the Flutter
SDK for development) and an **Android target** (Flutter Android apps
run on Chromebooks). Treat Chromebook support as part of Android
testing: check keyboard/mouse, resizable windows, and large-screen
layouts rather than assuming phone-shaped behaviour.

## Choosing platforms honestly

| Platform | Stable? | Builds on | Distribution shape |
|---|---|---|---|
| Android | Yes | Any host | AAB via Play (guide 10) |
| iOS | Yes | macOS only | IPA via App Store |
| Windows | Yes | Windows only | Release folder / MSIX (guide 09) |
| macOS | Yes | macOS only | .app in DMG / Mac App Store |
| Linux | Yes | Linux only | Bundle folder / package / Snap / Flatpak |
| Web | Yes | Any host | Static files from `build/web/` |

Supporting a platform is a testing commitment, not a checkbox: every
platform you enable needs its build in CI (on the right OS runner),
its release shape tested, and its quirks in your checklists. Start
with the platforms your users are actually on; adding one later with
`flutter create --platforms=… .` is routine.

## Checklist

- [ ] Web: Wasm build tried; JS fallback only for a named reason
- [ ] Web: routing/URLs and a non-Chrome browser checked
- [ ] Each desktop OS builds on its own OS runner in CI
- [ ] iOS/macOS signing and entitlements tested in the distribution build
- [ ] Linux/Windows whole-bundle (not single-binary) distribution verified

# 12 — Flavors and Configuration

A **flavor** (build configuration) is a named variant of your app —
`dev`, `staging`, `prod` — with its own app id, name, icon, and
settings, built from the same code. This guide covers how flavors
actually work per platform, and the simpler configuration tools
(`--dart-define`) that solve half the problems people reach for
flavors to solve.

Snapshot: **Flutter 3.50.0**. Platform support differs and matters:
Android flavors are mature; **Windows flavors need Flutter 3.47+**;
iOS/macOS flavors ride Xcode schemes/configurations.

## First: do you need flavors, or just configuration?

| Need | Tool |
|---|---|
| Different API URL / keys per environment, same app | `--dart-define` (below) — no flavor needed |
| Dev build installable next to prod on one device | Flavor (separate applicationId / bundle id) |
| Different app name/icon per environment | Flavor |
| White-label: same app, different branding per client | Flavor (+ per-flavor assets) |
| Feature toggles inside one build | Plain config in code / remote config — not flavors |

Flavors cost build-matrix time on every platform you support. Take
the cheaper tool when it does the job.

## --dart-define: compile-time configuration

```powershell
flutter run --dart-define=API_BASE=https://dev.example.com --dart-define=ENV=dev
flutter build appbundle --dart-define=API_BASE=https://api.example.com --dart-define=ENV=prod
```

Read it in code with the `String.fromEnvironment` family:

```dart
abstract final class AppConfig {
  static const env = String.fromEnvironment('ENV', defaultValue: 'dev');
  static const apiBase = String.fromEnvironment('API_BASE');
  static const isProd = env == 'prod';
}
```

Rules:

- Values are **compile-time constants**, baked into the build. They
  are not secrets — anyone with the binary can extract them. API
  *base URLs* and environment names are fine; private keys are not
  (there is no safe place for a private key inside a shipped app).
- For many values, use a JSON file instead of a long command line:
  `--dart-define-from-file=config/dev.json`.
- Keep one `AppConfig` as the only reader of `fromEnvironment`, so
  the rest of the app depends on a normal Dart class (testable,
  mockable) instead of scattered constants.

## The appFlavor constant

When flavors exist, Flutter/Gradle sets the flavor name at build
time and exposes it in Dart:

```dart
import 'package:flutter/foundation.dart';

// The flavor this build was compiled with, e.g. 'prod'; null if none.
final flavor = appFlavor;
```

Use it for flavour-level decisions (banner in dev builds, logging
level) — through your config class, not sprinkled across widgets.

## Android flavors (Gradle product flavors)

Defined in `android/app/build.gradle.kts`:

```kotlin
flavorDimensions += "env"
productFlavors {
    create("dev") {
        dimension = "env"
        applicationIdSuffix = ".dev"
        resValue("string", "app_name", "My App Dev")
    }
    create("prod") {
        dimension = "env"
    }
}
```

Build and run by name:

```powershell
flutter run --flavor dev -t lib/main_dev.dart
flutter build appbundle --release --flavor prod -t lib/main_prod.dart
```

Separate entry points (`main_dev.dart`, `main_prod.dart`) are the
standard pattern: each sets up its environment, then calls a shared
`runApp` with the real app widget. The `applicationIdSuffix` is what
lets dev and prod install side by side.

## iOS / macOS flavors

On Apple platforms a flavor = an **Xcode scheme + build
configuration** pair (dev/staging/prod schemes, each with its own
bundle id, name, and icon), created in Xcode. Flutter then honours
`--flavor <scheme name>`. It is more manual than Android's — budget
setup time, and name schemes exactly as you pass them on the command
line.

## Windows flavors

Windows flavor support arrived in **Flutter 3.47** (this pack's
snapshot, 3.50, includes it). Flavors are declared for the Windows
runner so `--flavor` selects the variant's name/icon/output. If you
are on an older Flutter, Windows has exactly one configuration —
upgrade rather than inventing workarounds.

## Icons per flavor

Different icons per flavor is the visible half of the pattern:

- Android: per-flavor `res` folders
  (`src/dev/res/mipmap-…`, `src/prod/res/mipmap-…`) — or generate all
  of them with the launcher-icons tooling per flavor config.
- Apple: separate app-icon asset catalogs per configuration, chosen
  by the scheme's build settings.
- Desktop: per-flavor icon files selected by the runner config.

A dev icon that is visibly different (banner, different colour) is a
safety feature, not decoration: it stops "I tested prod data with the
dev build" accidents.

## Putting it together: a sane default setup

- **Two flavors max to start** (`dev`, `prod`); add `staging` only
  when a real staging backend exists.
- Entry points per flavor, one shared app widget, one `AppConfig`.
- Environment values via `--dart-define-from-file`, one JSON per
  flavor, checked into the repo **without secrets** (public URLs and
  names only).
- CI builds each flavor on the platforms that support it, and the
  release pipeline only ever ships `prod` built from a clean checkout.

## Checklist

- [ ] Flavor-vs-dart-define decision made deliberately per need
- [ ] No secrets in dart-define values or flavor config files
- [ ] Dev and prod install side by side with visibly different icons
- [ ] One `AppConfig` class owns all environment reads
- [ ] Windows flavors only relied on with Flutter 3.47+

# 13 — Performance and DevTools

Flutter performance work has one golden rule: **measure in profile
mode, on a real device, with the built-in DevTools suite** — never
from debug mode, never from vibes. This guide covers the build modes,
the tools, and the small set of habits that prevent most jank.

Snapshot: **Flutter 3.50.0 / Dart 3.14.0**. **DevTools ships with the
Flutter SDK** — there is nothing separate to install.

## Build modes: debug, profile, release

| Mode | What it is for | Performance truth? |
|---|---|---|
| **Debug** | Day-to-day development: hot reload, asserts, debugger, service extensions | **No.** Debug is deliberately slower (JIT, checks, no optimisation) |
| **Profile** | Performance measurement: release-like AOT code, just enough service support for DevTools profiling | **Yes.** This is the mode you measure in |
| **Release** | Shipping: fully optimised, no debugger/profiler hooks | Yes, but you cannot profile it — profile mode exists precisely for this |

```powershell
flutter run --profile -d <device>
flutter build appbundle --release   # shipping (guide 10)
```

Judging frame times from a debug build is the most common Flutter
performance mistake. The second most common is measuring on an
emulator — use the slowest real device your users plausibly own.

## DevTools: the suite that ships with the SDK

Launch it from your IDE or with `flutter devtools` / the URL printed
by `flutter run`. The parts that matter most:

- **Performance view** — frame chart (UI thread + raster thread bars
  per frame), timeline events, and the "slow frame" story at a
  glance. A frame that misses its budget (about 16.6 ms at 60 Hz,
  8.3 ms at 120 Hz) shows up red.
- **CPU profiler** — where time actually goes in a recorded window;
  find the one expensive function instead of optimising ten cheap
  ones.
- **Memory view** — allocation tracking and snapshots; look for
  growth across repeated navigation (leaks in Flutter are usually
  undisposed controllers and subscriptions, see below).
- **Widget inspector** — the widget tree live, layout constraints,
  and "why is this rebuilding" questions; pair it with the
  inspector's rebuild indicators while profiling.
- **Network view** — every request your app made, timing and payload;
  pairs with [guide 06](06-networking-and-data.md).
- **Logging / debugger** — structured logs and breakpoints when the
  print statement is not enough.

Also new in this era: **Widget Previews are stable** (since Flutter
3.47) — the DevTools/IDE preview environment renders widgets outside
a running app, which is as much a design-iteration speed tool as a
performance one.

## Jank: what actually causes it

A frame has two budgets: build/layout/paint on the **UI thread**
(your Dart code) and rasterisation on the **raster thread** (drawing
the pixels). The Performance view tells you which thread missed —
fix the one that's red.

Usual suspects, in order:

1. **Doing real work in `build()`** — parsing, sorting, I/O, heavy
   computation. `build` should be a pure, cheap description of state;
   move work into your state/repository layer (guide 14).
2. **Rebuilding too much of the tree** — a state change at the top
   repainting a whole screen. Narrow the scope of listeners/builders
   so only the widgets that changed rebuild.
3. **Expensive paint** — big saveLayer effects (opacity over large
   areas, clips, blurs, shadows) hammer the raster thread.
   `RepaintBoundary` isolates a frequently-repainting region (an
   animation, a chart) so it does not force the rest of the screen to
   repaint with it:

   ```dart
   RepaintBoundary(child: AnimatedChart(data: data))
   ```

4. **Images at full size** — decoding a 4000px photo into a 200px
   slot wastes memory and time; size image requests to their display
   size.
5. **Synchronous I/O on the UI isolate** — use async APIs, or a
   background isolate (`compute`) for genuinely heavy CPU work.

## const discipline (the cheap 20%)

`const` constructors let Flutter skip rebuilding identical widget
subtrees entirely. It is the highest-value habit in this guide:

- Make every widget constructor `const`-capable (`const MyWidget({super.key})`).
- Use literal `const` widgets wherever values are static.
- Turn on the lint that nags you (it is in `flutter_lints`, see
  [guide 01](01-getting-started-and-toolchain.md) / reference) and
  let the analyser enforce the habit.

Related hygiene: dispose every `AnimationController`,
`TextEditingController`, `ScrollController`, stream subscription, and
timer in `dispose()` — undisposed resources are both a leak and a
jank source.

## Lists and scrolling

- Build long lists lazily with `ListView.builder` / `GridView.builder`
  (never a `Column` of 500 children).
- Give list items stable keys when their identity matters, so the
  framework reuses elements instead of rebuilding.
- Profile the scroll itself in profile mode; scroll jank is usually
  per-item build cost, so make the item widget cheap and `const`
  where possible.

## A repeatable performance pass

1. `flutter run --profile` on the slowest target device.
2. Script the exact interaction (scroll this list, open that screen).
3. Open DevTools Performance; find the red frames; note UI vs raster.
4. CPU-profile the worst window; fix the top offender only.
5. Re-measure the same script. Record before/after numbers in the
   change that fixes it — a fix without a measurement is a guess.
6. Check startup separately: time to first frame is its own budget;
   defer initialisation that the first screen does not need.

## Checklist

- [ ] All performance claims measured in profile mode on a real device
- [ ] DevTools Performance + CPU views used, worst offender fixed first
- [ ] No heavy work or I/O inside `build()`
- [ ] `const` used wherever possible; controllers/subscriptions disposed
- [ ] Animations/charts isolated with RepaintBoundary where they repaint often
- [ ] Long lists use builder constructors; images sized to their slots

# 14 — Architecture and Project Structure

Flutter's official guidance now includes a full app-architecture
recommendation (docs.flutter.dev/app-architecture) — this guide is the
short, opinionated version of it, matched to the rest of this pack:
unidirectional data flow, a repository between your UI and your data
sources, immutable UI state, and dependencies wired up in exactly one
place.

Snapshot: **Flutter 3.50.0 / Dart 3.14.0**. Package versions cited
here are in [reference/dependencies.md](../reference/dependencies.md)
— re-check them on pub.dev before pinning.

## The shape, in one picture

```
UI layer          Widgets + a state holder per screen
                  (reads immutable UI state, emits user intents)
        ▲  state down, events up  ▼
Data layer        Repositories  →  Services (API, database, prefs)
                  (one repository per data kind; the only place
                   that knows where data comes from)
```

- **Unidirectional data flow:** state flows down, events flow up.
  Widgets never mutate shared state directly.
- **Single source of truth:** each kind of data has exactly one owner
  (its repository). Two widgets needing the same data read the same
  repository, not two copies.
- **Separation that pays rent:** the UI does not know what an HTTP
  client or a SQL table is; the data layer does not know what a
  widget is. Either side can be tested and changed without the other.

## UI state: immutable, modelled, boring

Represent each screen's state as one immutable class — a sealed class
for distinct phases, or a single class with a status field — usually
generated with **freezed** (see guide 06 / dependencies reference) so
copying, equality, and pattern matching are correct by construction:

```dart
@freezed
sealed class NotesState with _$NotesState {
  const factory NotesState.loading() = NotesLoading;
  const factory NotesState.ready(List<Note> notes) = NotesReady;
  const factory NotesState.error(String message) = NotesError;
}
```

Why this matters: a widget that renders `state.when(loading: …,
ready: …, error: …)` cannot forget a case, and a state holder whose
whole job is "turn repository data into these states" is trivial to
unit test (guide 08).

## Feature-first vs layer-first folders

Two honest layouts; pick per project size:

**Layer-first** (fine for small apps):

```
lib/
  main.dart
  ui/            widgets, screens, state holders
  data/          repositories, services, models
  config/        AppConfig, routing
```

**Feature-first** (better once an app has several distinct areas —
each feature carries its own UI + state, sharing only the data layer):

```
lib/
  main.dart
  features/
    notes/       notes_screen.dart, notes_state.dart, notes_controller.dart
    settings/    …
  data/          repositories + services shared by features
  core/          config, routing, shared widgets, theme
```

Rule of thumb: start layer-first; the day one folder (usually `ui/`)
becomes a junk drawer, split by feature. Do not start a two-screen
app with a framework-grade folder cathedral.

## The repository pattern in practice

```dart
class NotesRepository {
  NotesRepository(this._api, this._db);
  final NotesApi _api;        // service: talks HTTP
  final NotesDao _db;         // service: talks the local database

  Stream<List<Note>> watchNotes() => _db.watchAll();   // UI reads local truth
  Future<void> refresh() async {                        // sync is the repo's job
    final remote = await _api.fetchNotes();
    await _db.replaceAll(remote);
  }
}
```

The UI watches the local source and asks for refreshes; caching,
offline behaviour, and "which source wins" live in exactly one class.
This is the same offline-first shape as [guide 07](07-local-storage.md)
describes — architecture and storage are the same decision.

## Dependency injection: one composition root

However you provide dependencies (provider, Riverpod, bloc, get_it —
see [guide 04](04-state-management.md) and the dependencies
reference), wire them in **one composition root**: `main.dart` (or a
`bootstrap.dart` it calls) constructs services → repositories → state
holders, in that order, and hands them to the app. Nothing else in
the codebase calls a constructor for a shared service or reaches into
a global locator mid-widget. Benefits you feel immediately:

- Tests substitute a fake repository at the root (guide 08).
- Platform setup (window manager on desktop, guide 09) and flavor
  config (guide 12) live at the root too, not scattered.
- "Where does this object come from?" always has the same answer.

## When NOT to add a package

The most valuable architecture skill is refusal:

- **Don't add a state-management package** for an app whose state is
  two screens and a settings flag — `StatefulWidget` + `ValueNotifier`
  / provider basics cover it; graduate when the pain is real
  (guide 04 helps you choose when it is).
- **Don't add a framework** (routing, DI, forms, all-in-one kits) to
  avoid learning the platform pieces this pack covers; every
  framework is a dependency you now track forever.
- **Don't abstract a service you have one implementation of** behind
  an interface "for later" — abstract at the second implementation
  or at the test boundary, whichever comes first.
- **Don't add code generation** (freezed/json_serializable are worth
  it — guide 06) for three hand-written models; add it when the
  model count makes hand-writing the error-prone option.
- **Check maintenance before anything:** a package whose last release
  is years old (the dependencies reference flags the famous ones) is
  a liability, however many blog posts recommend it.

Every package you *do* add: pin it in pubspec, note why in the commit,
and re-check it at upgrade time with `flutter pub outdated`
(reference/commands.md).

## Growing without collapsing

- Keep `main.dart` thin: bootstrap, then `runApp`.
- One routing definition for the whole app (guide 05).
- Shared widgets graduate to `core/` only when a second feature needs
  them — not on first use, not "just in case".
- Let the analyser be the architecture police: strict lints on
  (guide 01), no bypassing with ignore-comments as a habit.
- Re-read this guide at each new feature and ask: which layer does
  this belong to, and who owns its data? If the answer is unclear,
  the structure — not the feature — is the work.

## Checklist

- [ ] Data flows one way: state down, events up; one owner per data kind
- [ ] Screen states are immutable modelled classes (freezed where it pays)
- [ ] Repositories are the only place that know data sources
- [ ] All wiring happens in one composition root
- [ ] Folder layout matches project size (layer-first small, feature-first grown)
- [ ] Every package in pubspec has a reason; stale packages refused

# Flutter pack — scripts

PowerShell 7 scripts (the pack's primary shell, matching the DevTools
house rules) with a bash twin of each for Git Bash / WSL / macOS /
Linux. Every script is check-and-report by default: **nothing here
installs anything, downloads anything (except
`Update-FlutterPack -Fetch`, only when you pass the switch), or stores
credentials.**

| Script | What it does |
|---|---|
| [Test-FlutterToolchain.ps1](Test-FlutterToolchain.ps1) / [.sh](Test-FlutterToolchain.sh) | Read-only readiness check: flutter/dart on PATH + versions, git, Visual Studio C++ workload (via vswhere), Android SDK pieces (ANDROID_HOME, cmdline-tools, platform-tools, platforms), Chrome for web. Prints a PASS/MISSING table with the exact fix step per miss, then summarizes `flutter doctor -v`. Exit 1 if anything is missing. |
| [New-FlutterProject.ps1](New-FlutterProject.ps1) / [.sh](New-FlutterProject.sh) | Wraps `flutter create` with pack defaults: `-Name` (required, lowercase_with_underscores), `-Org` (default `com.example`), `-Platforms` (default `windows,android`), `-Empty` switch. Refuses if flutter is missing or the folder exists. Applies `templates/analysis_options.yaml` and `templates/gitignore-flutter` when present, then prints next steps. |
| [Invoke-FlutterBuild.ps1](Invoke-FlutterBuild.ps1) / [.sh](Invoke-FlutterBuild.sh) | Builds one target — `windows-release`, `android-aab`, `android-apk-debug`, `web` — then reports the artifact path, size, and SHA256 (Windows: Release folder + app exe hash; AAB/APK: the file hash; web: folder + `main.dart.js` hash). Fails clearly on a nonzero build exit or a missing artifact. |
| [Update-FlutterPack.ps1](Update-FlutterPack.ps1) / [.sh](Update-FlutterPack.sh) | Pack maintenance. Default (no network): prints the Flutter releases manifest URL and the pub.dev API endpoint for every package in `reference/dependencies.md` so the version snapshot can be re-verified by hand. With `-Fetch` / `--fetch` only: downloads the releases manifest and compares the current stable Flutter against `reference/versions.md`. Writes nothing either way. |

## Usage

```powershell
pwsh -File scripts/Test-FlutterToolchain.ps1
pwsh -File scripts/New-FlutterProject.ps1 -Name my_app -Org com.acme
pwsh -File scripts/Invoke-FlutterBuild.ps1 -Target android-aab -ProjectPath .\my_app
pwsh -File scripts/Update-FlutterPack.ps1            # offline
pwsh -File scripts/Update-FlutterPack.ps1 -Fetch     # the only network mode in this folder
```

```bash
bash scripts/Test-FlutterToolchain.sh
bash scripts/New-FlutterProject.sh my_app --org com.acme
bash scripts/Invoke-FlutterBuild.sh --target android-aab --project ./my_app
bash scripts/Update-FlutterPack.sh --fetch
```

Copy-and-start material for Flutter projects. Versions match the

| Template | What it is | How to use it |
|---|---|---|

## Notes

- The app skeleton's `pubspec.yaml` carries the optional
  dependencies (provider / Riverpod, go_router, dio / http, drift,
  freezed / json_serializable, build_runner, mocktail) as comments

  a version hunt.
- The skeleton's SDK constraint is `sdk: ^3.14.0`. Dart accepts the

  does not.
- Nothing in these templates contains secrets, signing keys, or
  machine-specific paths. Release signing belongs in CI secrets /
  Play App Signing, never in a template.

# Fixtures

Synthetic test data and model fixtures for Flutter work. Everything
here is made up — names, emails (`.invalid` domains), and URLs are
placeholders, safe to commit and share.

| Fixture | What it is | Use it for |
|---|---|---|
| [sample-data/items.json](sample-data/items.json) | Five sample items matching the app skeleton's `SampleItem` shape (camelCase fields: `id`, `title`, `subtitle`, `isFavorite`, `ownerId`, `createdAt`) | Loading into the skeleton's repository in tests, seeding a local database, stubbing an API response |
| [sample-data/users.json](sample-data/users.json) | Three sample users (`id`, `displayName`, `email`, `avatarUrl`, `isPro`, `joinedAt`); item `ownerId` values reference these ids | Owner/author lookups in tests, profile UI with fake data |
| [dart/sample_item.dart](dart/sample_item.dart) | A hand-written plain Dart model with the items' shape, plus — clearly labelled in comments — the `@freezed` source it is modelled on and what the generator would emit | Seeing the model shape without running codegen; the file is explicit about what is hand-written vs generated, and ships no fake generated output |

## Conventions

- Field names are Dart/JSON camelCase (`isFavorite`, `ownerId`,
  `createdAt`), matching Dart model classes and `fromJson` code —
  unlike snake_case fixtures you may know from other packs.
- Dates are UTC ISO 8601 strings ending in `Z`, the form
  `DateTime.parse` accepts directly.
- Ids are small sequential integers, consistent across files:
  `items.ownerId` points at `users.id`.
